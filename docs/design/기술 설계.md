# 기술 설계

요건서와 실행 설계를 구현 가능한 수준으로 내린 기술 정의와 전체 로직입니다. 이 탭을 기준으로 작업 플랜을 작성합니다.

## 1. 기술 스택과 패키지 구조

`orch`는 표준 라이브러리만으로 동작하는 Python CLI로 만듭니다. 외부 의존성을 두지 않아 Intel 맥에서 설치와 유지가 단순하고, 실행 시점의 실패 원인을 줄일 수 있습니다.

**기술 스택**

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 언어·런타임 | Python 3.14 이상 | `tomllib`, 개선된 `subprocess`, 타입 힌트 |
| 패키징·설치 | `uv`, `uv tool install` | 허브를 전역 명령으로 설치 |
| CLI | `argparse` | 외부 의존성 없음 |
| 상태 저장 | `sqlite3` (WAL 모드) | 여러 프로세스의 동시 갱신을 트랜잭션으로 처리 |
| 설정 | `tomllib` | `targets.toml`, `~/.orch/config`, 지시서 메타데이터를 같은 형식으로 |
| 스키마 검증 | 자체 검증 함수 (`dataclasses` 기반) | 결과·리뷰 JSON의 필드가 적어 라이브러리가 불필요 |
| 프로세스 제어 | `subprocess` + 프로세스 그룹 | 시간 상한과 강제 종료를 Python이 직접 처리 |
| 외부 도구 | `git`, `gh`, `codex`, `claude`, `tmux` | 모두 서브프로세스로 호출 |
| 테스트 | `pytest` (개발 전용) | 실행 환경에는 설치하지 않음 |

**설계 원칙**

1. **상태의 원본은 `state.db` 하나**입니다. `TODO.md`, `orch status` 출력은 모두 여기서 파생합니다.
2. **판정 근거는 파일과 git**입니다. 결과 JSON, 리뷰 JSON, git diff, 테스트 실행 결과로만 상태를 바꿉니다.
3. **메인이 읽는 출력은 JSON 한 줄**입니다. 메인(LLM)이 해석을 틀릴 여지를 줄이고 토큰을 아낍니다.
4. **외부 도구 호출은 어댑터 뒤에 둡니다.** `git`, `gh`, 에이전트 CLI, 터미널을 각각 한 모듈에서만 호출해, 테스트 시 가짜로 바꾸기 쉽게 합니다.
5. **모든 쓰기는 원자적으로** 합니다. 파일은 임시 파일에 쓴 뒤 이름을 바꾸고, DB는 `BEGIN IMMEDIATE` 트랜잭션으로 갱신합니다.

**패키지 구조**

## 2. 데이터 모델과 파일 규격

작업(task)과 실행(run)을 분리합니다. 작업은 생애주기 전체의 상태를, 실행은 서브를 한 번 돌린 기록을 담습니다. 재시도는 같은 작업의 두 번째 실행입니다.

**SQLite 스키마**

```sql
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;

CREATE TABLE tasks (
  id              TEXT PRIMARY KEY,          -- 브랜치명 task/<id>와 동일
  target          TEXT NOT NULL,             -- targets.toml의 대상명
  title           TEXT NOT NULL,
  grade           TEXT NOT NULL,             -- L1 | L2 | L3 | L3R (위험 영역)
  lane            TEXT NOT NULL,             -- B | C | D
  model           TEXT NOT NULL,
  effort          TEXT,                      -- low | medium | high | xhigh
  state           TEXT NOT NULL,             -- 3장 상태 머신
  attempt         INTEGER NOT NULL DEFAULT 0,
  timeout_sec     INTEGER NOT NULL,
  base_sha        TEXT,                      -- 작업 시작 시 origin/main
  test_sha        TEXT,                      -- 메인이 넣은 테스트·인터페이스 스텁 커밋
  depends_on      TEXT,                      -- JSON 배열 (선행 작업 id)
  worktree        TEXT,
  pr_url          TEXT,
  slot_expires_at TEXT,                      -- 슬롯 예약 만료 시각
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL
);

CREATE TABLE runs (
  run_id          INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id         TEXT NOT NULL REFERENCES tasks(id),
  attempt         INTEGER NOT NULL,
  lane            TEXT NOT NULL,
  model           TEXT NOT NULL,
  effort          TEXT,
  pid             INTEGER,                   -- 프로세스 그룹 리더
  pid_started_at  TEXT,                      -- pid 재사용 오판 방지
  started_at      TEXT,
  ended_at        TEXT,
  exit_code       INTEGER,
  outcome         TEXT,                      -- DONE | PARTIAL | FAILED | BLOCKED | BLOCKED_QUOTA
  failure_reason  TEXT
);

CREATE TABLE locks (
  target          TEXT NOT NULL,
  path_glob       TEXT NOT NULL,             -- 수정 범위 (glob)
  task_id         TEXT NOT NULL REFERENCES tasks(id),
  PRIMARY KEY (target, path_glob, task_id)
);

CREATE TABLE gate_results (
  task_id TEXT, attempt INTEGER, gate TEXT,  -- G1 | G2 | G3 | G2_PRE_PR
  passed INTEGER, detail TEXT, at TEXT,
  PRIMARY KEY (task_id, attempt, gate)
);

CREATE TABLE events (                        -- 감사 기록, 상태 전이마다 1행
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id TEXT, from_state TEXT, to_state TEXT, actor TEXT, note TEXT, at TEXT
);
```

- 마지막 push 커밋: 스키마 v2에서 `ALTER TABLE tasks ADD COLUMN pushed_sha TEXT`를 추가합니다(M8에서 적용, 기존 데이터를 바꾸지 않는 추가형 변경). `orch pr`와 `orch update`가 push에 성공할 때마다 기록하며, 브랜치 갱신의 lease 값으로 씁니다. 원격 추적 브랜치(`origin/task/<id>`)는 `fetch`만으로 바뀌어 lease의 보호가 사라지므로 쓰지 않습니다.
- 동시 실행 슬롯은 별도 테이블 없이 `tasks.state`가 `reserved` 또는 `running`인 행을 레인별로 세어 판정합니다.
- 잠금 충돌은 glob 겹침으로 판정합니다. 두 glob이 같은 파일을 가리킬 수 있으면 충돌로 봅니다(보수적 판정).
- `runs`는 매핑표와 동시 실행 상한을 조정하는 데이터로도 씁니다.

**지시서 메타데이터 (TOML 앞머리)**

지시서 맨 앞에 `+++`로 감싼 TOML 블록을 둡니다. 표준 라이브러리 `tomllib`로 읽을 수 있어 YAML 파서를 추가하지 않아도 됩니다.

```
+++
id = "feat-login-form"
title = "Add the login form"
target = "sample-app"
grade = "L2"
lane = "B"
model = "gpt-6.1-sol"
effort = "medium"
timeout_min = 45
modify = ["src/auth/**"]
read = ["src/**", "docs/auth.md"]
verify = "npm test -- auth"
depends_on = []
+++

# 목적
...
# 확정 사실
...
```

- `orch`는 앞머리만 읽고, 본문(목적, 확정 사실, 인터페이스, 중단 조건, 금지 사항)은 서브에게 그대로 전달합니다.
- `title`은 필수이며 `tasks.title`에 저장합니다. 게이트의 커밋 메시지와 PR 제목으로 그대로 쓰므로 영어로 씁니다. 출력 가능한 ASCII 한 줄, 72자 이내만 허용합니다.
- `modify`에 대상의 `shared_paths`나 테스트 파일이 포함되면 등록을 거부합니다.
- 선택 필드 `review = true`는 등급만으로는 리뷰하지 않는 작업에 리뷰를 추가합니다(위험 영역). 리뷰를 더할 수만 있으며, L3와 L3R은 `review = false`여도 항상 리뷰합니다.
- `verify`는 네트워크 없이, 워크트리 밖에 쓰지 않고 동작해야 합니다. 서브가 샌드박스 안에서 실행하기 때문입니다. Python 대상이면 `.venv/bin/python -m pytest ...` 형식으로 씁니다.
- 결과 JSON과 리뷰 JSON은 요건 탭 7장 규격을 그대로 따릅니다.

## 3. 작업 상태 머신

작업 상태는 `tasks.state` 하나로 표현하고, 모든 전이는 `orch` 명령을 통해서만 일어납니다. 전이마다 `events`에 기록이 남습니다. 아래 전이 규칙은 `models.py`의 데이터 하나로 정의하고, `store.py`의 조건부 전이는 같은 표로 허용 여부를 판정합니다.

**정상 경로**: `prepared` → `reserved`(또는 `queued`) → `running` → `judging` → `gating` → (`reviewing`) → `ready` → `pr_open` → `closed`

**상태 정의**

| 상태 | 의미 | 다음 행동 주체 |
| --- | --- | --- |
| `prepared` | 브랜치·워크트리 생성됨. 메인이 인터페이스·테스트를 작성 중 | 메인 |
| `queued` | 등록됐지만 슬롯 부족 또는 선행 작업 미완료 | `orch` (슬롯 반환 시) |
| `reserved` | 슬롯 예약됨. `orch run` 시작 대기 (예약 10분 후 만료) | 메인 |
| `running` | 서브 실행 중 | 서브 |
| `judging` | 실행 종료, 결과 기록됨. 메인의 판정 대기 | 메인 |
| `gating` | 게이트 실행 중 | `orch` |
| `reviewing` | 교차 리뷰 진행 중 | 리뷰 서브 |
| `ready` | 게이트·리뷰 통과. PR 생성 대기 | 메인 |
| `conflict` | PR 전 rebase 충돌, 또는 열린 PR이 main과 충돌 | 메인 |
| `pr_open` | PR 생성됨. 머지 대기 | 사용자, 검증 세션 |
| `closed` | PR 머지 후 정리 완료 (종료 상태) | — |
| `blocked` | 서브 `BLOCKED` 또는 `BLOCKED_QUOTA`, 또는 의존 작업이 `discarded`. 워크트리·잠금 보존 | 사용자 |
| `discarded` | 폐기됨 (종료 상태) | — |
| `orphaned` | 실행 중이었으나 프로세스가 사라짐 (메인 재시작 등) | 사용자 |

**전이 규칙**

| 현재 | 계기 | 다음 |
| --- | --- | --- |
| `prepared` | `orch dispatch` + 슬롯·잠금·의존 충족 | `reserved` |
| `prepared` | `orch dispatch` + 조건 미충족 | `queued` |
| `prepared`, `queued`, `reserved` | `orch discard` | `discarded` |
| `queued` | 다른 작업 종료로 조건 충족 → `orch next`가 예약 | `reserved` |
| `queued` | 의존 작업이 `discarded` → `orch dispatch`·`orch next`가 판정 | `blocked` |
| `reserved` | `orch run` 시작 / 예약 만료 | `running` / `queued` |
| `running` | 프로세스 종료 (결과 분류 완료) | `judging` |
| `judging` | 결과 `DONE` → `orch gate` | `gating` |
| `judging` | 결과 `FAILED`·`PARTIAL`, 시도 1회차 → `orch retry` | `reserved` (attempt 2), 슬롯이 없으면 `queued` (attempt 2) |
| `judging` | 결과 `FAILED`·`PARTIAL`, 시도 2회차 → `orch discard` | `discarded` |
| `judging` | 결과 `BLOCKED`·`BLOCKED_QUOTA` → `orch run`이 결과 기록 직후 전이 | `blocked` |
| `gating` | 통과 + 리뷰 필요 (L3 이상·위험 영역) | `reviewing` |
| `gating` | 통과 + 리뷰 불필요 | `ready` |
| `gating` | 실패 | `judging` (실패로 간주, 재시도 규칙 적용) |
| `reviewing` | `orch review save`: `PASS` / `BLOCK` | `ready` / `judging` (실패로 간주) |
| `reviewing` | `orch review save --triage`: `BLOCK`을 분류해 넘김 (4.6) | `ready` |
| `ready` | `orch pr` 성공 / rebase 충돌 | `pr_open` / `conflict` |
| `ready` | PR 전 G2 실패 (`G2_PRE_PR`) | `judging` (실패로 간주, 재시도 규칙 적용) |
| `conflict` | 메인이 해결 후 `orch pr` 재실행 / 설계 수준 충돌로 폐기 | `pr_open` / `discarded` |
| `conflict` | 충돌 해결 후 PR 전 G2 실패 (`G2_PRE_PR`) | `judging` (실패로 간주, 재시도 규칙 적용) |
| `pr_open` | `orch update`에서 main과 충돌 | `conflict` |
| `pr_open` | 머지 확인 후 `orch close` | `closed` |
| `pr_open` | 사용자가 머지하지 않고 PR을 닫음 → `orch discard` | `discarded` |
| `blocked` | 사용자 승인으로 `orch resume` / `orch discard` | `reserved`, 슬롯이 없으면 `queued` / `discarded` |
| `running` | SessionStart 복구에서 프로세스 부재 확인 | `orphaned` |
| `orphaned` | 사용자 지시로 `orch resume` / `orch discard` | `reserved`, 슬롯이 없으면 `queued` / `discarded` |

- 종료 상태(`closed`, `discarded`)가 되면 잠금을 해제하고 `queued` 작업의 실행 가능 여부를 다시 판정합니다.
- 재시도는 작업당 1회입니다(`attempt` 최대 2). 게이트 실패, 리뷰 `BLOCK`, PR 전 G2 실패도 같은 횟수를 공유합니다. `orch resume`은 `attempt`를 소모하지 않습니다.
- 의존 작업이 여전히 `discarded`이면 `orch resume`은 작업을 다시 `blocked`로 보냅니다.

## 4. 핵심 처리 로직

명령별 처리 순서입니다. 각 단계가 실패하면 그 시점의 상태를 유지한 채 오류 JSON을 반환하고, 부분적으로 바뀐 것은 되돌립니다.

### 4.1 orch prepare — 작업 준비

메인이 테스트를 먼저 쓸 수 있도록, 배분 전에 브랜치와 워크트리를 만드는 단계입니다.

1. 지시서 앞머리를 파싱하고 검증합니다 (필수 키, 레인·모델·강도 조합이 매핑표와 맞는지, `modify`에 공유 파일·테스트 파일이 없는지). `depends_on`의 id가 같은 대상의 작업으로 등록돼 있지 않으면 거부합니다. 오타가 영원한 대기로 이어지는 것을 막기 위함이며, 선행 작업을 먼저 `prepare`해야 하므로 순환 의존도 생기지 않습니다. 검증한 지시서는 `tasks/<id>.md`에 저장합니다.
2. `git fetch origin` 후 `origin/<기본 브랜치>`를 `base_sha`로 기록합니다.
3. `task/<id>` 브랜치로 `~/.orch/<대상>/worktrees/<id>`에 워크트리를 만들고, 샌드박스 밖에서 대상의 `setup_command`를 워크트리에서 실행합니다(허브는 `uv sync --frozen`).
4. 상태를 `prepared`로 등록하고 워크트리 경로를 반환합니다. 메인은 여기에 테스트와 인터페이스 스텁(본문은 `raise NotImplementedError`)을 쓰고 커밋합니다.

### 4.2 orch dispatch / orch next — 배분과 슬롯

1. 워크트리에 `base_sha` 이후 커밋이 1개 이상 있는지 확인하고, 그 커밋을 `test_sha`로 기록합니다. 테스트 커밋이 없으면 거부합니다 (L1 중 테스트가 불필요한 작업은 지시서에 `tests = "none"`으로 명시해야 통과).
2. `BEGIN IMMEDIATE` 트랜잭션 안에서 판정합니다.
   - 선행 작업(`depends_on`)이 모두 `closed`인가
   - `modify` glob이 다른 활성 작업의 잠금과 겹치지 않는가
   - 레인별 슬롯이 남았는가 (B+C+D 합계 3, B 2)
3. 판정과 잠금은 다음 순서를 따릅니다. 결과는 `{"state": "reserved"}` 또는 `{"state": "queued", "waiting_for": [...]}`로 반환합니다.
   - **의존 미충족**: 잠금을 잡지 않고 `queued`로 둡니다. 선행 작업과 수정 범위가 겹치는 후속 작업이 먼저 배분돼도, 후속 작업이 잠금을 쥔 채 선행 작업을 막는 교착이 생기지 않습니다.
   - **의존 충족, 잠금 겹침**: 잠금을 잡지 않고 `queued`로 둡니다.
   - **의존 충족, 잠금 가능, 슬롯 없음**: 잠금을 등록하고 `queued`로 둡니다.
   - **모두 충족**: 잠금을 등록하고 `reserved`(예약 만료 10분)로 둡니다.
   - 의존이 이미 충족된 `queued` 작업(재시도, 예약 만료, 슬롯 대기)만 잠금을 유지합니다. 겹침 판정에서 자기 잠금은 제외합니다.
4. `orch next`는 `queued` 작업 전체를 `created_at` 오래된 순으로 같은 기준에 따라 다시 판정해, 새로 `reserved`가 된 작업 목록을 반환합니다. 메인은 완료 알림을 받을 때마다 호출합니다.
5. `orch next`와 `orch status`는 막힌 작업도 보여 줍니다. 이번에 `blocked`가 된 작업, 그리고 `blocked`인 작업을 직접 또는 사슬로 기다려 `queued`에 머무는 작업을 원인 작업 id와 함께 반환합니다. 사슬로 기다리는 작업은 상태를 바꾸지 않습니다. 설계상 `blocked`로 가는 계기는 `discarded` 의존뿐이기 때문입니다.

### 4.3 orch run — 실행과 결과 분류

메인이 백그라운드 셸로 호출합니다. 이 프로세스가 끝나는 것이 곧 완료 통지입니다.

1. 상태가 `reserved`인지 확인하고 `running`으로 바꾼 뒤 `runs` 행을 만듭니다.
2. 레인 어댑터가 명령을 만듭니다. 지시서 본문 뒤에 공통 규칙(결과 JSON 경로와 형식, 커밋 금지, 백그라운드 실행 금지, 테스트 파일 수정 금지)을 덧붙여 표준 입력으로 넘깁니다.
3. `subprocess.Popen(start_new_session=True)`로 새 프로세스 그룹에서 실행하고, pid와 프로세스 시작 시각을 기록합니다. 출력은 로그 파일로 보냅니다.
4. 시간 상한까지 기다립니다. 넘으면 그룹 전체와 자손 프로세스에 SIGTERM, 10초 후에도 남아 있으면 SIGKILL을 보냅니다. Codex는 도구 명령을 별도 세션으로 실행하므로 프로세스 그룹만으로는 부족합니다. 자손 목록은 Codex가 끝나면 찾을 수 없으므로 신호를 보내기 전에 구합니다.
5. 워크트리의 `.orch-result.json`을 `results/<id>.json`으로 옮기고, 결과를 아래 순서로 분류합니다. 먼저 맞는 규칙이 이깁니다.

| 순서 | 조건 | outcome / failure\_reason |
| --- | --- | --- |
| 1 | `orch`가 시간 상한으로 종료시킴 | `FAILED` / `timeout` |
| 2 | 외부 신호로 종료 (SIGKILL 등, 메모리 정리 포함) | `FAILED` / `killed` |
| 3 | 결과 JSON이 유효하고 `DONE`인데 수정 범위 밖 변경이나 테스트 파일 변경이 있음 | `FAILED` / `out_of_scope` |
| 4 | 결과 JSON이 유효함 | 결과 JSON 값 |
| 5 | 유효한 결과 JSON이 없고, 제공자의 구조화된 오류가 한도 오류임 | `BLOCKED_QUOTA` |
| 6 | 유효한 결과 JSON이 없고, 로그의 오류 메시지나 끝부분에 한도 문구가 있음 (제공자별 패턴, 설정 파일로 관리) | `BLOCKED_QUOTA` |
| 7 | 그 외 | `FAILED` / `report_missing` |

한도 판정은 유효한 결과 JSON이 없을 때만 합니다. 로그 전체를 문구로 검색하면 지시서 출력이나 코드에 있는 `quota` 같은 단어 때문에 `DONE`이 `BLOCKED_QUOTA`로 바뀌기 때문입니다.

- **구조화된 오류 (Codex, 5번)**: `codex exec --json` 출력의 `thread.started`에서 `thread_id`를 얻고, `$CODEX_HOME/sessions/**/rollout-*-<thread_id>.jsonl`에서 마지막 `task_complete`의 `error.codex_error_info`를 읽습니다. 값이 `usage_limit_exceeded`이면 한도 오류입니다. `--json` 출력 자체에는 이 필드가 없고 메시지만 있습니다.
- **대체 수단 (6번)**: rollout 파일이 없거나 형식이 다르면, 또는 `codex_error_info`가 `other`이면 문구를 검색합니다. JSON 로그는 `error`와 `turn.failed` 이벤트의 메시지만 검색하고, JSON이 아닌 로그(C 레인)는 지시서 출력을 뺀 끝부분을 검색합니다.
- **한도 오류가 아닌 경우**: 재시도가 소진된 `response_too_many_failed_attempts`(HTTP 429 포함), `internal_server_error`는 `report_missing`으로 분류합니다.
- rollout 파일은 공개 계약이 아니므로, 고정한 Codex 버전을 올릴 때 다시 확인합니다. 근거는 codex-cli 0.160.0과 로컬 모의 서버 시험이며, 실제 서버의 한도 응답은 재현하지 않았습니다.

6. 분류 결과를 결과 JSON에 반영해 다시 쓰고(원자적 쓰기), `runs`와 `tasks`를 한 트랜잭션으로 갱신해 `judging`으로 바꿉니다. 슬롯을 반환하고 `TODO.md`를 다시 만듭니다. 결과가 `BLOCKED`·`BLOCKED_QUOTA`이면 `orch run`이 이어서 `lifecycle`의 전이 함수로 `blocked`로 옮깁니다. `runner`는 이 전이를 하지 않습니다. `blocked`로 옮긴 뒤 `orch run`이 `quota` 또는 `blocked` 알림을 보냅니다(4.12). 알림 실패는 분류, 전이, 종료 코드를 바꾸지 않습니다.
7. 상태별 종료 코드로 끝납니다. 단, 메인은 종료 코드가 아니라 결과 JSON으로 판정합니다.

### 4.4 orch wait — D 레인 대기

1. 대화형 패널을 띄운 뒤, 워크트리에 `.orch-result.json`이 생기거나 시간 상한에 도달할 때까지 5초 간격으로 확인합니다. 이 주기 점검은 `orch` 내부에서만 일어나며 메인의 토큰을 쓰지 않습니다.
2. 패널이 먼저 닫히면 `FAILED` / `report_missing`으로 처리합니다.
3. 이후 분류와 갱신은 4.3의 5\~7단계와 같습니다.

### 4.5 orch gate — 검증 게이트

시작 전에, `reviews/<id>.json`의 판정이 `BLOCK`이면 거부합니다. 게이트를 다시 돌려 리뷰를 다시 받는 우회를 막기 위함이며, 재시도가 이 파일을 보관 위치로 옮기면 거부가 풀립니다.

1. **G1 범위**: `test_sha` 이후의 모든 변경(커밋되지 않은 변경과 새 파일 포함, `git diff --name-only <test_sha>`와 `git ls-files --others --exclude-standard`)이 `modify` glob에 들어가는지, 테스트 파일(`tests/**`)과 `shared_paths`를 건드리지 않았는지 확인합니다. `.orch-result.json`은 검사에서 제외합니다.
2. **G2 테스트**: 대상의 `test_command`와 지시서의 `verify`를 워크트리에서 실행합니다 (각 15분 상한).
3. **G3 정적 검사**: 대상의 `lint_command`를 실행합니다. 설정이 없으면 건너뜁니다.
4. 앞 단계가 실패하면 뒤 단계는 실행하지 않습니다. 결과는 `gate_results`에 남기고 `{"passed": false, "failed_gate": "G2", "detail": "요약"}` 형태로 반환합니다.
5. 통과하면 서브의 변경을 작업 브랜치에 커밋하고, 등급과 위험 영역 여부로 리뷰 필요성을 판정해 `reviewing` 또는 `ready`로 바꿉니다.

### 4.6 리뷰

- **Codex 구현분 → Claude 리뷰**: `orch-reviewer`의 도구는 `Read`, `Grep`, `Glob`뿐이므로, 메인이 diff를 `reviews/<id>.diff`로 저장해 경로를 넘깁니다. 메인이 이 서브에이전트를 백그라운드로 실행하고, 서브에이전트가 반환한 리뷰 JSON을 `orch review save <id>`에 표준 입력으로 넘겨 저장합니다.
- **Claude 구현분 → Codex 리뷰**: 메인이 `orch review <id> --by codex`를 백그라운드 셸로 실행합니다. `codex exec`를 읽기 전용 샌드박스로 돌리고, 마지막 메시지에서 리뷰 JSON을 추출해 저장합니다.
- 저장 시 스키마를 검증하고, P0·P1이 있으면 `BLOCK`, 없으면 `PASS`로 확정합니다. P2·P3는 전이의 `events` 기록에 백로그로 남깁니다.
- `orch review save`는 `reviewing` 상태에서만 동작합니다.

**`BLOCK` 분류와 경로**

메인은 리뷰 JSON을 받으면 저장하기 전에 P0·P1 지적을 지시서와 코드에 대조해 분류합니다. 요건 9장의 분류에 따라 경로가 갈립니다.

| 분류 | 명령 | 이후 |
| --- | --- | --- |
| 구현 결함 | `orch review save <id>` | `judging` → `orch retry`. 2회차의 `BLOCK`은 `orch discard` |
| 테스트가 틀림, 또는 테스트 부족과 구현 결함 | `orch review save <id>` | `judging` → 재시도 없이 `orch discard`, 테스트를 고쳐 새 id로 배분. 기다리던 작업은 `blocked` |
| 잘못된 지적 | `orch review save <id> --triage <파일>` | `ready` → `orch pr` |
| 구현은 맞고 테스트만 부족함 | `orch review save <id> --triage <파일>` | `ready` → `orch pr`. 후속 작업이 테스트를 추가 |

**확인된 구현 결함은 triage로 넘길 수 없습니다.** P0·P1 중 하나라도 구현 결함으로 확인되면 다른 지적이 어떻든 `--triage` 없이 저장해 재시도나 폐기로 보냅니다. 한 리뷰의 지적들이 잘못된 지적과 테스트 부족으로만 나뉘면 지적마다 판단을 적어 함께 넘깁니다.

**triage 파일**: `reviews/<id>.triage.md`에 저장합니다. TOML 앞머리와 자유 형식 본문으로 이뤄지며, PR 본문에 들어가므로 영어로 씁니다.

```
+++
follow_up = "feat-login-form-tests"  # insufficient_tests 판단이 있으면 필수, 없으면 금지

[[decisions]]
severity = "P1"
path = "tests/test_login.py"
verdict = "insufficient_tests"       # wrong_finding | insufficient_tests
decision = "The implementation handles this case; only a check is missing."

[[decisions]]
severity = "P0"
path = "src/auth/form.py"
verdict = "wrong_finding"
decision = "The value is validated by the caller, so this input cannot occur."
+++
```

`orch review save`는 아래 중 하나라도 어기면 거부하고 상태를 바꾸지 않습니다.

- 판정이 `BLOCK`입니다. `PASS`에는 triage를 쓰지 않습니다.
- 처리하지 않은 P0·P1이 없습니다. `decisions`와 리뷰의 P0·P1 지적을 `(severity, path)`로 개수까지 맞춰 일대일로 대조하고, 남는 지적이나 남는 판단이 있으면 거부합니다.
- 판단마다 `verdict`가 두 값 중 하나이고, `decision`이 비어 있지 않습니다.
- `verdict = insufficient_tests`인 판단의 `path`는 `tests/`로 시작합니다.
- `insufficient_tests` 판단이 하나라도 있으면 `follow_up`이 있고, 그 작업이 같은 대상에 등록돼 있으며 `discarded`가 아닙니다. 그런 판단이 없으면 `follow_up`을 적을 수 없습니다.

### 4.7 orch pr — PR 생성

`orch pr`, `orch update`, `orch close`의 흐름은 `prflow.py`에 둡니다. `github.py`는 `gh` 호출만, `gitops.py`는 git 호출만 맡습니다.

1. 상태가 `ready`인지 확인합니다. 리뷰가 필요한 작업(등급 또는 `review = true`)은 저장된 리뷰가 있어야 합니다. 저장된 판정이 `BLOCK`이면 유효한 triage 파일이 있어야 하고, 대상 저장소에 `review-overridden` 라벨이 있어야 합니다. `orch`는 이 라벨을 만들지 않고 있는지만 확인합니다. 없으면 rebase와 push 전에 오류로 멈추고 상태를 바꾸지 않습니다. 라벨은 사용자가 저장소마다 한 번 만들어 둡니다.
2. `git fetch origin` 후 `origin/<기본 브랜치>` 위로 rebase합니다. 충돌이 나면 rebase를 중단하고 `conflict`로 바꾼 뒤 충돌 파일 목록을 반환합니다.
3. G2를 다시 실행합니다(`G2_PRE_PR`). 실패하면 `judging`으로 되돌립니다.
4. 작업 브랜치만 push합니다. 판단 기준은 상태가 아니라 `pushed_sha`의 존재입니다. `pushed_sha`가 없으면 `git push -u origin task/<id>`를 쓰며, force push 없이 원격 브랜치가 이미 다르게 존재하면 오류로 멈춥니다. `pushed_sha`가 있으면 이미 push된 브랜치이므로 `gitops.update_task_branch`로 갱신합니다(4.7.1 5번). 성공하면 push한 커밋을 `pushed_sha`에 기록합니다.
5. `gh pr create`로 PR을 만듭니다. 제목과 본문은 영어 템플릿으로 생성하고, 본문에 작업 요약, 변경 파일, 게이트 결과, 리뷰 판정을 넣습니다. `BLOCK`을 넘긴 PR은 본문 맨 위에 `Review BLOCK overridden` 섹션(후속 작업, 지적별 `verdict`와 판단)을 두고 `review-overridden` 라벨을 붙입니다.
6. `pr_url`을 기록하고 `pr_open`으로 바꿉니다.
7. 연 PR의 Merge by가 `user check`인지 판정해(4.12) JSON 출력에 `user_check`(참/거짓)로 더하고, 참이면 `needs_review` 알림을 보냅니다. 판정은 `prflow.user_check`가 맡습니다. 알림 실패는 1~6의 결과와 `user_check` 값을 바꾸지 않습니다.

### 4.7.1 orch update — 열린 PR의 브랜치 갱신

PR이 열려 있는 동안 `origin/<기본 브랜치>`가 움직이면 실행합니다. 상태가 `pr_open`이 아니면 거부합니다.

1. `git fetch origin` 후 워크트리에서 최신 기본 브랜치를 임시로 합칩니다(`git merge --no-ff --no-edit`).
2. **충돌이 없으면 push하지 않습니다.** 임시 결과에서 게이트를 실행하고, 결과와 상관없이 `pushed_sha`로 되돌려 임시 결과를 버립니다. 통과하면 상태는 `pr_open` 그대로입니다. 실패하면 PR에 `Integration check failed against the latest main. Do not merge.` 코멘트를 `redact`를 거쳐 남기고, 결과를 보고하며, 메인이 판단합니다. G1은 임시 병합의 첫 부모를 작업의 마지막 커밋으로 보고, 기본 브랜치에서 들어온 파일을 범위 검사에 넣지 않습니다.
3. **충돌이 있으면** 병합을 중단하고 `conflict`로 바꾼 뒤 충돌 파일 목록을 반환합니다. 메인이 `origin/<기본 브랜치>` 위로 rebase해 해결합니다. 설계 수준의 충돌이면 `discarded`로 보냅니다.
4. 해결한 뒤 `orch pr <id>`를 다시 실행합니다. 게이트를 다시 통과해야 하고, 해결이 로직을 바꿨으며 작업이 L3 이상이면 다시 리뷰합니다.
5. 이미 push된 브랜치는 `pushed_sha`가 있는지로 판단해 `gitops.update_task_branch`로 갱신합니다. force push의 유일한 예외이며 다음 조건을 코드로 강제합니다. `task/<id>` 브랜치만 허용합니다. 명령은 `git push --force-with-lease=task/<id>:<pushed_sha> origin task/<id>:refs/heads/task/<id>` 형식만 쓰고, lease 값이 없는 `--force`나 `--force-with-lease`는 쓰지 않습니다.
6. 갱신에 성공하면 `pushed_sha`를 새 커밋으로 바꾸고, 해결 내용을 PR 코멘트로 남긴 뒤 `pr_open`으로 바꿉니다.

### 4.7.2 orch wait --merged — 머지 대기

`orch pr` 뒤 메인은 `orch wait <id> --merged`를 백그라운드 셸로 실행하고 턴을 끝냅니다. 이 명령이 끝나면 완료 알림이 메인의 새 턴을 엽니다. 폴링은 이 명령이 하며 메인은 폴링하지 않습니다.

- 시작할 때와 확인할 때마다 작업이 `pr_open` 또는 `conflict`이고 `pr_url`이 있는지 봅니다. 아니면 64로 거부합니다. 상태를 바꾸지 않으며 슬롯과 잠금을 잡지 않습니다.
- `--interval <초>`(기본 60) 간격으로 봇 토큰을 사용해 `github.pull_request_status`로 PR 상태를 확인합니다. 토큰은 만료되므로 확인할 때마다 새로 발급하고, 하위 프로세스의 `GH_TOKEN`으로만 넘깁니다.
- `--max-wait <분>`(양의 정수, 기본 90)은 대기 상한입니다. 남은 시간이 간격보다 짧으면 남은 시간만 쉬고 한 번 더 확인합니다. 그래도 머지되거나 닫히지 않았으면 60으로 끝납니다.
- 머지되면 0, 머지 없이 닫히면 50, 대기 상한에 도달하면 60으로 끝납니다. 출력은 다른 명령과 같은 JSON 한 줄이며 `task_id`, `state`, `pr_url`, `pr_state`, `merged`, `merged_at`, `checks`를 담습니다. `pr_state`는 마지막으로 성공한 확인의 PR 상태이고, 성공한 확인이 없으면 `null`입니다. 일시적인 확인 실패는 다음 간격에 다시 시도하고, 10회 연속 실패하면 70으로 끝납니다. 두 한도가 같은 확인에서 겹치면 70이 먼저입니다.
- 완료 알림의 종료 코드는 판정에 쓰지 않습니다. 메인은 JSON 출력을 읽고 `orch close` 또는 `orch discard`를 실행하며, 두 명령이 PR 상태를 다시 확인합니다. `orch close` 뒤에는 `orch next`로 다음 작업을 이어 갑니다. 대기 상한에 도달했거나 완료 알림에 출력이 없으면 같은 명령을 다시 걸어 둡니다.
- `conflict` 상태에서 PR이 머지되면 이 명령은 0으로 끝나지만 `orch close`는 `pr_open`만 받으므로 거부합니다. 이 경우 메인은 멈추고 보고합니다.
- 메인이 재시작되면 이 명령도 사라집니다. 복구 요약의 `pr_open` 작업에 다시 걸어 둡니다.
- D 레인의 `orch wait <id>`는 별도 동작이며, 그것이 구현되기 전까지 `--merged`는 필수입니다.

### 4.8 orch close / retry / discard / kill

- **close**: `gh pr view`로 머지 여부를 확인합니다. 머지됐으면 워크트리 제거, 로컬 브랜치 삭제, 잠금 해제 후 `closed`. 머지 전이면 거부합니다.
- **retry**: `judging` 상태, `attempt`가 1이고 실패 근거(`DONE`이 아닌 결과, 실패한 게이트, `BLOCK` 리뷰)가 있을 때만 허용합니다. 워크트리를 `test_sha`로 되돌리고(`git reset --hard`와 `git clean -fd`, 워크트리 내부에서만, `.orch-result.json`도 제거), 지시서 끝에 이전 실패 요약과 `unresolved`, 실패한 게이트, `BLOCK`의 P0·P1 지적을 덧붙인 뒤 슬롯을 다시 예약합니다. 슬롯이 없으면 `queued`로 둡니다. `attempt`는 2가 됩니다. 이전 리뷰와 triage 파일은 `reviews/attempts/<id>.<attempt>.json`, `reviews/attempts/<id>.<attempt>.triage.md`로 옮겨, 2회차가 이전 판정을 재사용하지 못하게 합니다. id에 `.`이 허용되므로 현재 파일과 같은 디렉터리에 두지 않습니다.
- **resume**: `blocked`, `orphaned`에서만 허용하며 사용자 승인 후에 실행합니다. 기본 동작은 retry와 같은 방법으로 워크트리를 `test_sha`로 되돌리는 것입니다. 한도 소진 후 재개나 지시서를 고친 재실행 모두 부분 변경을 남기면 안 되기 때문입니다. 변경을 유지하려면 `--keep`을 명시합니다. `attempt`를 소모하지 않고, 지시서에 실패 요약을 덧붙이지 않으며, 슬롯이 없으면 `queued`로 둡니다.
- **discard**: 워크트리와 로컬 브랜치를 제거하고 잠금을 해제한 뒤 `discarded`로 바꿉니다. 원격에 push된 브랜치는 건드리지 않습니다. `pr_url`이 있으면 `gh pr view`로 확인해, PR이 닫혀 있을 때만 폐기합니다. 열려 있거나 머지된 PR은 거부합니다.
- **kill**: 프로세스 그룹을 종료하고 `FAILED` / `aborted`로 기록합니다. 워크트리는 보존합니다. `orch doctor`가 멈춘 작업 처리에 쓰므로 M15 착수 전에 구현합니다.

### 4.9 복구 (SessionStart 훅)

1. `running` 작업마다 pid가 살아 있고 프로세스 시작 시각이 기록과 같은지 확인합니다. 아니면 `orphaned`로 바꿉니다.
2. 만료된 `reserved` 예약은 `queued`로 되돌립니다.
3. `judging`, `blocked`, `orphaned`, `conflict`, `pr_open` 작업을 요약해 메인 컨텍스트에 주입합니다. 메인은 이 요약을 보고 판정을 이어갑니다.

- 1과 2는 모든 대상의 작업에 적용합니다. pid와 시작 시각으로 판정하므로 다른 대상의 살아 있는 작업은 바뀌지 않습니다. 3의 요약은 `ORCH_TARGET`의 작업만 담습니다.
- 프로세스 시작 시각은 `orch run`이 `runs.pid_started_at`을 기록할 때와 같은 방법(`runner.process_started_at`)으로 읽습니다. 조회할 수 없으면 프로세스가 없는 것으로 봅니다.
- 상태 전이는 다른 명령과 같이 조건부 UPDATE로 합니다. 그 사이 `orch run`이 끝나 `judging`으로 옮겼다면 그 작업은 건너뜁니다.
- 토큰과 네트워크를 쓰지 않습니다. 실패해도 세션 시작을 막지 않습니다(5.3 실패 처리).

### 4.10 orch doctor — 상시 운용 점검

launchd가 10분마다 실행합니다. 점검 항목마다 정상·경고·장애를 판정하고, 상태가 나빠진 항목만 `doctor_<항목>` 이벤트로 알려(4.12) 같은 알림이 반복되지 않게 합니다.

| 점검 | 방법 | 장애 시 조치 |
| --- | --- | --- |
| 메인 세션 | 터미널 어댑터로 `orch-<대상>` 세션과 메인 프로세스 존재 확인 | 세션 재기동 시도 후 알림 |
| Claude Code 인증 | 짧은 비대화형 호출 또는 인증 상태 명령으로 확인 (사용량 소모가 없는 방법을 고정 버전에서 확정) | 새 배분 중단, 알림 |
| Codex 인증 | 로그인 상태 확인 명령 | 새 배분 중단, 알림 |
| `gh` 인증 | `gh auth status` | PR 생성 중단, 알림 |
| 디스크 | `~/.orch/` 볼륨의 여유 공간 (기본 10GB 미만이면 경고) | `orch gc` 즉시 실행, 부족하면 새 배분 중단 |
| 네트워크 | Tailscale 상태 확인 | 알림 (복구는 Tailscale 자체 재연결에 맡김) |
| 멈춘 작업 | `running`인데 시간 상한을 넘긴 작업 | `orch kill` 처리 후 알림 |

"새 배분 중단"은 `state.db`의 전역 플래그로 두고, `orch dispatch`와 `orch next`가 이 플래그를 확인합니다. 원인이 해소되면 다음 점검에서 플래그를 자동으로 내립니다.

### 4.11 render와 orch watch — 파생 화면

`TODO.md`, `orch status --human`, `orch watch`는 모두 `state.db`에서 파생하며 상태를 바꾸지 않습니다. 내용을 만드는 함수는 `render.py`에 두고, 현재 시각을 인자로 받아 같은 입력에 같은 출력을 냅니다.

**TODO.md**

- 위치는 런타임 디렉터리의 `~/.orch/<대상>/TODO.md` 하나입니다. 저장소 작업 트리(허브 클론, 대상 저장소의 기본 작업 트리, 워크트리)에는 만들지 않습니다. 허브 저장소가 공개이므로 유출을 막고, 허브 클론을 더럽히지 않기 위함입니다.
- 같은 디렉터리의 임시 파일에 쓴 뒤 `os.replace`로 바꿉니다. 임시 파일 이름은 쓰는 프로세스마다 달라야 하고, 실패하면 임시 파일을 지웁니다. 여러 프로세스가 동시에 써도 읽는 쪽은 항상 완성된 파일만 봅니다. 이 성질은 테스트로 고정합니다.
- 동시에 쓰면 마지막에 바뀐 파일이 남으므로 잠시 뒤처진 내용일 수 있습니다. 다음 명령이 다시 만들며, 상태의 원본은 언제나 `state.db`입니다.
- 내용은 "자동 생성, 직접 수정 금지" 안내, 작업 표(id, 제목, 상태, 등급, 레인, 시도 횟수, 경과 시간, 헤드 커밋, PR), `blocked_chains`입니다. 경로, 로그, 결과 요약, 리뷰 내용은 넣지 않습니다.
- `orch run`이 작업을 `running`으로 바꾼 직후와 실행을 끝낸 직후, 그리고 상태를 바꾸는 다른 명령이 끝날 때 다시 만듭니다.
- 다시 만들기에 실패하면 표준 오류에 경고만 남깁니다. 명령의 JSON 출력, 종료 코드, 상태 전이는 바꾸지 않습니다.

**상태 요약과 PR 본문**

- `orch status`의 각 작업에 `elapsed_sec`와 `head_sha`를 더합니다. `elapsed_sec`는 `created_at`부터 현재까지이고, `closed`와 `discarded`는 `updated_at`까지입니다. `head_sha`는 `pushed_sha`이며 push 전에는 `null`입니다.
- `orch status --human`도 같은 값을 보여 줍니다.
- `orch pr`의 JSON 출력에 push한 커밋을 `head_sha`로 더합니다.
- PR 본문 생성은 `prflow.build_body`에서 `render`로 옮기며 내용은 그대로입니다. 제목, 본문, 코멘트의 `redact`는 지금처럼 `github.py`가 전송 직전에 적용합니다. 이 경로가 유지되는지 테스트로 고정합니다.

**orch watch**

- 사용자가 터미널에서 직접 실행하는 앞단 상태판입니다. `--interval <초>`(양의 정수, 기본 2) 간격으로 `ORCH_TARGET`의 작업 표를 다시 그리고, `--once`를 주면 한 번만 그리고 끝납니다. Ctrl-C로 끝나면 종료 코드는 0입니다.
- 기본 동작은 터미널 어댑터를 쓰지 않습니다. M13에서 `--panels`를 추가합니다. 이 옵션을 주면 매 간격마다 `ORCH_TARGET`의 `running` 작업마다 그 실행의 `logs/<id>.<n>.log`를 `tail -F`로 보여 주는 패널을 `terminal_split`으로 열고, 작업이 `running`을 벗어나면 그 패널을 닫습니다. 패널은 어댑터가 기록한 것만 닫습니다(5.2). tmux 세션 밖에서 `--panels`를 주면 64로 거부합니다.
- 상태를 바꾸지 않고, 슬롯과 잠금을 잡지 않으며, 토큰과 네트워크를 쓰지 않습니다.
- 연결은 `store.connect`를 씁니다. SQLite의 읽기 전용 열기는 WAL의 `-shm` 파일이 없으면 실패합니다.
- 출력은 사람이 읽는 형식이며 JSON이 아닙니다. 표준 출력이 터미널일 때만 화면을 지웁니다. 한 번의 조회가 실패하면 오류를 표시하고 다음 간격에 다시 시도합니다.

### 4.12 notify — 알림 전송

알림 수단은 ntfy.sh 무료 플랜입니다. 원칙은 **사용자가 조치해야 할 때만** 알리는 것입니다. 작업 완료, PR 생성, 머지, 복구처럼 사용자가 할 일이 없는 일은 알리지 않습니다.

**이벤트**

| 이벤트 종류 | 보내는 곳 | 조건 | 구현 |
| --- | --- | --- | --- |
| `quota` | `orch run` | 실행 결과가 `BLOCKED_QUOTA`로 분류되어 `blocked`로 바뀔 때 | m-notify |
| `blocked` | `orch run` | 실행 결과가 `BLOCKED`로 분류되어 `blocked`로 바뀔 때 | m-notify |
| `needs_review` | `orch pr` | 연 PR의 Merge by가 `user check`일 때 | m-notify |
| `input_wait` | `orch hook notification` | Claude Code의 Notification 훅이 권한 요청을 알릴 때(matcher `permission_prompt`, 입력의 `notification_type`도 같은 값). 중복 억제 키의 작업 id 자리는 `main`. 본문에는 알림 메시지를 넣지 않음 | M14 |
| `doctor_<항목>` | `orch doctor` | 점검 항목이 정상에서 경고로, 경고에서 장애로 나빠질 때만 (4.10) | M15 |

- `needs_review`의 `user check` 판정은 PR에 `review-overridden` 라벨을 붙였거나, 변경 파일이 안전 장치 경로에 걸릴 때입니다. 변경 파일은 `origin/<기본 브랜치>`와의 merge-base부터 push한 커밋까지 바뀐 파일입니다.
- 안전 장치 경로 목록은 `targets.toml`의 대상별 `safety_paths`에 한 번만 둡니다. `needs_review` 판정은 이 목록만 기준으로 하며, 다른 곳에 목록을 복제하지 않습니다. 허브 대상의 목록은 `CLAUDE.md`의 Merge policy가 가리키는 목록입니다(`orchestrator` 대상의 `safety_paths`).
- `safety_paths`의 형식은 `shared_paths`와 같습니다. 저장소 루트 기준 상대 경로의 목록이며, 항목은 파일 하나이거나 `/` 또는 `/**`로 끝나는 디렉터리입니다. 그 밖의 `*`, `?`, 절대 경로, `..`는 거부합니다. 변경 파일이 항목과 같거나 그 디렉터리 아래에 있으면 걸립니다. 생략하면 빈 목록이며, 그때는 `review-overridden` 라벨만으로 판정합니다. `Target.safety_paths`로 읽습니다.
- `safety_paths` 키는 v0.4.0부터 읽습니다. v0.3.0의 `load_targets`는 모르는 키를 거부하므로, 허브의 `targets.toml`에는 v0.4.0을 설치한 뒤에 추가합니다.
- `orch` 밖에서 만드는 하네스 PR에는 이 알림이 가지 않습니다.

**설정**

```toml
[notify]
method = "ntfy"
topic = "<길고 무작위적인 이름>"
```

- 토픽은 전체가 `[A-Za-z0-9_-]{20,64}`에 맞아야 하며, 아니면 `config.load_config`가 토픽 값을 넣지 않은 `ConfigError`를 냅니다. `/`나 `?`가 들어가면 전송 URL이 바뀌고, 짧은 토픽은 추측하기 쉬우며 본문에 우연히 들어가 `redact`가 매번 거부하기 때문입니다.
- 토픽은 `~/.orch/config`에만 둡니다. 저장소, 지시서, 로그, PR 본문에는 넣지 않습니다. 토픽을 아는 사람은 누구나 구독하고 발행할 수 있으므로 토픽 이름이 곧 비밀입니다.
- `method`는 `"none"` 또는 `"ntfy"`이며 기본은 `"none"`입니다. `"ntfy"`이면 `topic`이 필수이고, `"none"`이면 `topic`을 둘 수 없습니다(`config.load_config`의 기존 검증). `[notify]`가 없거나 `method = "none"`이면 알림을 보내지 않습니다. 명령의 결과는 바뀌지 않습니다.
- 권한 검사는 `method = "ntfy"`일 때만 합니다. `~/.orch/config`가 0600보다 넓게 열려 있으면(`st_mode & 0o077`이 0이 아니면) 표준 오류에 경고하고 보내지 않습니다. `method = "none"`이면 파일 권한과 관계없이 보내지 않으며 경고도 하지 않습니다.

**본문과 전송**

- 본문에는 대상, 작업 id, 이벤트 종류만 담습니다. 작업이 없는 이벤트는 작업 id를 비웁니다.
- 본문은 전송 전에 `redact(text, home=…, orch_home=…, secrets=[토픽])`를 거칩니다. `redact`가 예외를 내면 보내지 않고 실패로 처리합니다.
- 표준 라이브러리 `urllib.request`로 `https://ntfy.sh/<토픽>`에 POST합니다. 시간 제한은 5초입니다.
- 시간 초과를 포함한 모든 전송 실패는 표준 오류의 경고로 기록만 하고, 원래 명령의 JSON 출력, 종료 코드, 상태 전이를 바꾸지 않습니다. URL에 토픽이 들어가므로 경고와 예외 메시지에도 같은 `redact`를 적용합니다.

**중복 억제**

- 같은 키의 알림은 30분 안에 한 번만 보냅니다. 키는 이벤트마다 다르며, 서로 다른 작업의 알림은 서로 억제하지 않습니다.

| 이벤트 | 중복 억제 키 | 이유 |
| --- | --- | --- |
| `quota` | 이벤트 종류 | 원인이 계정 단위라 대상과 작업이 달라도 같은 원인 |
| `doctor_<항목>` | 대상 + 항목 | 점검 항목 단위 |
| `blocked`, `needs_review`, `input_wait` | 대상 + 이벤트 종류 + 작업 id | 작업마다 사용자가 따로 조치해야 함 |

- 작업 id가 없는 알림(예: 메인 세션의 권한 요청)은 작업 id를 빈 값으로 둔 키를 씁니다.
- 키별 마지막 전송 시각은 `~/.orch/notify.json`(`config.notify_state_path`)에 기록합니다. 전송이 성공했을 때만 갱신하므로, 실패한 알림은 다음 발생 때 다시 보냅니다. 쓰기는 `TODO.md`와 같이 임시 파일에 쓴 뒤 `os.replace`로 바꿉니다. 파일이 없거나 읽을 수 없으면 기록이 없는 것으로 보고 보냅니다. 두 프로세스가 동시에 보내 한 번 더 가는 경우는 허용합니다.
- 30분 판정은 현재 시각을 인자로 받는 함수로 두어 테스트에서 시각을 고정합니다.

**orch notify test**

- 설정을 확인하기 위해 사용자가 직접 실행하는 시험 전송입니다. 이벤트 종류는 `test`이고 대상과 작업 id는 비웁니다. 대상을 읽지 않으므로 `ORCH_TARGET`과 `ORCH_HUB`가 없어도 됩니다.
- 중복 억제를 거치지 않고, `notify.json`을 읽거나 갱신하지 않습니다. 본문의 `redact`, 5초 시간 제한, 권한 검사는 일반 알림과 같습니다.
- 결과는 JSON 한 줄의 `result`로 냅니다. `sent`(전송 성공), `disabled`(`[notify]`가 없거나 `method = "none"`), `refused_permissions`(0600 검사 실패), `failed`(`redact` 예외, 시간 초과를 포함한 전송 실패) 중 하나입니다. `sent`이면 `{"ok": true, "result": "sent"}`와 종료 코드 0, 나머지는 `{"ok": false, "error": "<result 값>", "result": "<result 값>", "message": "…"}`와 종료 코드 20입니다. 출력에는 토픽을 넣지 않습니다.

**테스트**

- 네트워크를 쓰지 않습니다. 전송 함수(transport)를 인자로 주입한 가짜로 바꾸고, `urllib.request.urlopen`은 호출되면 실패하도록 패치합니다. 시간 초과와 실패가 원래 명령의 결과를 바꾸지 않는지, 토픽이 출력과 경고에 남지 않는지 확인합니다.
- CLI 연결은 프로세스 안의 `orch` 픽스처와 monkeypatch로 시험합니다. 환경 변수로 가짜 전송을 켜는 장치는 두지 않습니다.

## 5. CLI 계약, H2 실행과 훅, 동시성

### 5.1 CLI 출력과 종료 코드

- 메인이 호출하는 명령은 표준 출력에 **JSON 한 줄**만 씁니다. 사람이 읽는 출력은 `--human` 옵션으로만 냅니다.
- 공통 형식: 성공은 `{"ok": true, ...}`, 실패는 `{"ok": false, "error": "코드", "message": "한국어 설명"}`입니다.
- 대상은 환경 변수 `ORCH_TARGET`으로 정합니다. `orch open`이 메인 세션에 이 값을 넣어 두므로, 메인은 명령마다 대상을 지정하지 않습니다.
- 허브 위치는 환경 변수 `ORCH_HUB`로 정합니다. `uv tool install`로 설치한 패키지는 허브 위치를 알 수 없으므로, `targets.toml`을 읽는 명령은 이 값이 없으면 거부합니다. `orch open`이 메인 세션에 이 값을 넣고, `orch open`은 이 값이 없으면 실행 중인 셸의 값을 씁니다.
- `orch hook <이름>`은 Claude Code가 호출하므로 이 JSON 형식을 따르지 않고 5.3의 훅 형식을 따릅니다.
- `ORCH_FAKE_AGENTS=1`은 `~/.orch`가 아닌 `ORCH_HOME`이 명시됐을 때만 허용합니다. 그렇지 않으면 `cli.py`가 64로 거부합니다. 환경 변수가 잘못 남아도 실제 상태 저장소에서 가짜 에이전트가 돌지 않게 하기 위함입니다.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 성공 (`orch run`에서는 `DONE`) |
| 10 | `PARTIAL` |
| 20 | `FAILED`, `orch notify test`에서 `sent`가 아닌 결과 |
| 30 | `BLOCKED` |
| 40 | `BLOCKED_QUOTA` |
| 50 | `orch wait --merged`에서 PR이 머지 없이 닫힘 |
| 60 | `orch wait --merged`에서 대기 상한 도달. 다시 걸어 둠 |
| 64 | 잘못된 사용 (인자, 상태 전이 위반), 원격 브랜치가 옮겨져 lease push가 거부됨 |
| 70 | 내부 오류 |

### 5.2 orch open (H2)

1. `targets.toml`에서 대상을 찾고, 대상 저장소의 원격 정보를 확인합니다. 사용자가 기본 작업 트리를 편집 중일 수 있으므로, 미커밋 변경은 경고만 합니다.
2. `~/.orch/config`의 `[agents] claude` 절대 경로로 `claude --version`을 실행해 고정 버전과 비교합니다. 다르거나 확인할 수 없으면 경고만 하고 계속합니다. 고정 버전은 `launcher.py`의 상수 한 곳에 두며, 지금 값은 `2.1.319`입니다. 이 값을 바꾸는 것은 PR로 하고, `launcher.py`가 안전 장치 경로이므로 user check입니다.
3. 터미널 어댑터로 `orch-<대상>` 세션을 엽니다. 이미 있으면 그 세션에 다시 붙고, 메인을 새로 실행하지 않습니다.
4. 세션의 첫 패널(메인 패널)에서 대상 저장소 위치를 작업 디렉터리로, 환경 변수 `ORCH_TARGET`, `ORCH_HUB`를 설정해 메인 Claude Code를 실행합니다. `claude`는 2의 절대 경로로 실행합니다. 셸 문자열을 조립하지 않고 인자 목록으로 넘깁니다.
5. 같은 세션에 관찰 패널을 엽니다: `orch watch --panels`, `tail -F ~/.orch/<대상>/logs/subagents.log`. `TODO.md`는 패널로 열지 않습니다(같은 내용을 `orch watch`가 보여 줌).

**주입 옵션 (Claude Code 2.1.319에서 확인)**

| 옵션 | 값 | 시점 |
| --- | --- | --- |
| `--model` | `claude-opus-5-5` | M13 |
| `--settings` | `<허브>/config/settings.json` (훅, 접근 금지 규칙) | M13 |
| `--add-dir` | `~/.orch/<대상>` (펼친 절대 경로) | M13 |
| `--remote-control` | 이름 없음. claude.ai에서 메인 세션에 접속 | M13 |
| `--append-system-prompt-file` | `<허브>/config/main.md` | M16 |
| `--agents` | `config/agents/`를 변환한 JSON | M16 |

- M16 전에는 메인 규칙과 서브에이전트 정의를 주입하지 않습니다. 허브를 대상으로 열면 작업 디렉터리의 `CLAUDE.md`, `AGENTS.md`, `.claude/agents/`가 원래대로 읽힙니다. 다른 대상을 여는 것은 M16 이후입니다.
- `--add-dir`은 메인 세션의 읽기 범위를 넓히는 용도이며 메인 Claude Code에만 붙입니다. Codex 서브에 `--add-dir`을 쓰지 않는 규칙(실행 설계 3장)과는 별개이고, 그 규칙을 바꾸지 않습니다.
- 주입 옵션의 정확한 형식은 `launcher.py` 한 곳에서만 조립하므로, Claude Code 버전이 바뀌어도 이 파일만 고치면 됩니다. `launcher.py`는 실행하지 않고 인자 목록, 작업 디렉터리, 환경 변수, 경고를 돌려주는 순수 함수로 두고, 실행은 `cli.py`가 어댑터로 합니다.

**자동 업데이트**: Claude Code 자동 업데이트는 끕니다. 네이티브 설치본 하나를 모든 세션이 같이 쓰므로, `orch open`의 `--settings`만으로는 다른 세션의 업데이트를 막지 못합니다. 그래서 사용자가 사용자 설정(`~/.claude/settings.json`)의 `env`에 `DISABLE_AUTOUPDATER=1`을 넣습니다. 업데이트는 사용자가 확인한 뒤 직접 실행하고, 같은 PR로 고정 버전을 올립니다. 2의 경고는 이 절차가 빠졌을 때의 안전망입니다.

**탈출구**: 훅은 `orch open`이 `--settings`로 주입할 때만 걸립니다. 훅이나 설정이 잘못되어 메인이 일을 못 하면, 사용자는 `orch open` 없이 허브에서 `claude`를 직접 실행해 훅 없는 세션으로 고칠 수 있습니다. 같은 이유로 훅을 `.claude/settings.json`에 두지 않습니다. 그 파일은 작업 워크트리에도 들어가 C 레인 서브에 걸리기 때문입니다.

**터미널 어댑터의 창 기록**

- 어댑터는 자기가 만든 세션의 메인 패널 id와, 자기가 만든 창·패널 id를 `~/.orch/<대상>/terminal.json`에 기록합니다. 임시 파일에 쓴 뒤 `os.replace`로 바꿉니다.
- `terminal_send`는 기록된 창·패널 중 메인 패널이 아닌 id에만 보냅니다. 기록에 없는 id나 메인 패널 id면 아무것도 보내지 않고 예외를 냅니다. 메인 대화에 입력이 끼어들지 않게 하기 위함입니다.
- 패널을 닫는 것도 기록된 id만 하고, 메인 패널은 닫지 않습니다.
- tmux는 인자 목록으로 호출하고 셸을 거치지 않습니다. 테스트는 가짜 실행기만 쓰고 실제 tmux 서버에 닿지 않습니다. 실제 tmux는 설치 후 실환경 확인에서만 씁니다.

### 5.3 훅 구현

훅은 모두 `orch hook <이름>` 하위 명령으로 구현하고, 허브의 `config/settings.json`에서 이 명령을 가리킵니다. Claude Code가 표준 입력으로 넘기는 JSON을 읽어 처리하고, Claude Code의 훅 출력 형식으로 답합니다.

| 훅 | 명령 | 처리 |
| --- | --- | --- |
| SessionStart | `orch hook session-start` | 4.9 복구를 수행하고, 요약을 `hookSpecificOutput.additionalContext`로 돌려줘 메인 컨텍스트에 주입 |
| PreToolUse (matcher `Bash`) | `orch hook pre-bash` | `guard.py`로 `tool_input.command`를 판정. 차단은 `permissionDecision: "deny"`, 사용자 확인은 `"ask"`, 사유는 `permissionDecisionReason`에 한국어로. 통과면 아무것도 출력하지 않음 (`"allow"`를 내면 권한 확인을 건너뛰므로 내지 않음) |
| SubagentStop | `orch hook subagent-stop` | `agent_type`과 `last_assistant_message`의 앞 500자를 한 줄로 바꿔 시각과 함께 `~/.orch/<대상>/logs/subagents.log`에 추가 |
| Notification (matcher `permission_prompt`) | `orch hook notification` | `notification_type`이 `permission_prompt`일 때만 4.12의 `input_wait`를 보내고, 그 밖의 알림(유휴 대기 등)은 무시 |

**pre-bash 판정 (`guard.py`)**

- 명령을 제어 연산자(`;`, `&&`, `||`, `|`, `&`, 줄바꿈, 괄호, `$(...)`, 백틱)로 나눈 단순 명령마다 판정합니다. 앞의 `이름=값` 할당과 감싸는 명령(`env`, `command`, `exec`, `nohup`, `time`, `sudo`)은 건너뛰고, 실행 파일은 경로의 마지막 이름으로 비교합니다. `bash`, `sh`, `zsh`의 `-c` 인자는 다시 판정합니다.
- 차단(`deny`):
  - `codex` 실행
  - `claude`에 `-p` 또는 `--print`
  - `git push`에 `--force`, `-f`(묶인 짧은 옵션 포함), `--force-with-lease`, `--force-if-includes`, 또는 `+`로 시작하는 refspec. `git -C <경로> push`도 같음
  - `gh pr merge`
  - `gh api`의 인자 중 PR 머지 경로(`repos/<소유자>/<저장소>/pulls/<번호>/merge`, 앞의 `/` 유무와 무관)
  - 어떤 인자든 `~/.orch/secrets`를 가리키는 경우 (`~`, `$HOME`, `${HOME}`, 펼친 홈 경로 형태)
- 사용자 확인(`ask`): `orch resume`. 사용자 승인 뒤에만 실행한다는 규칙을 훅이 강제합니다.
- `orch` 안에서 실행되는 `codex`, `git push`는 훅이 보는 명령이 아니므로 영향이 없습니다.
- **설정을 읽지 않습니다.** `orch hook pre-bash` 경로는 `~/.orch/config`, `targets.toml`, `state.db`를 읽지 않고, 표준 입력과 환경 변수 `HOME`만 씁니다. 설정이 깨져도 Bash 전체가 막히지 않게 하기 위함입니다.
- 이 판정은 실수로 레인을 우회하는 것을 막는 장치이며 보안 경계가 아닙니다. 변수 펼치기나 `eval`로 숨긴 명령은 막지 못합니다.

**실패 처리**

- **Claude Code의 종료 코드 처리 (2.1.319에서 실측):** PreToolUse 훅이 도구 실행을 막는 경우는 종료 코드 2, 또는 종료 코드 0과 `permissionDecision: "deny"` 출력 두 가지뿐입니다. 종료 코드 1·70 같은 다른 비정상 종료, 파이썬 비정상 종료, 명령 없음(127), JSON이 아닌 출력, 훅 시간 초과는 모두 실행을 **허용**합니다. 그래서 pre-bash에서 처리되지 않은 예외는 곧 "실패 시 허용"이 되며, 아래 규칙은 이를 막기 위한 것입니다.
- pre-bash는 닫힌 쪽으로 실패합니다.
  - 입력 JSON이 깨졌거나, 따옴표가 닫히지 않아 명령을 나눌 수 없거나, 내부 오류가 나면 `deny`와 사유를 돌려줍니다.
  - `orch hook pre-bash`는 표준 입력 읽기와 처리기에서 나는 모든 예외(`BaseException`, `KeyboardInterrupt`·`SystemExit` 포함)에 `deny`를 출력합니다. 표준 출력에 쓰지 못하면 표준 오류에 사유를 쓰고 종료 코드 2로 끝납니다.
  - `orch` 프로세스가 `_hook`에 닿기 전에 실패하는 경우(`PATH`에 `orch`가 없음, import 오류 등)는 `config/settings.json`의 명령 `orch hook pre-bash || exit 2`가 종료 코드 2로 바꿉니다. 이때는 Bash 전체가 막히므로 5.2의 탈출구를 씁니다.
  - 훅 시간 초과(10초)는 Claude Code가 허용으로 처리하므로 막을 수 없습니다. 판정은 문자열 처리만 하므로 보통 수십 밀리초 안에 끝납니다.
- 나머지 세 훅은 열린 쪽으로 실패합니다. 표준 입력 읽기, 처리기, 표준 출력 쓰기에서 나는 모든 예외(`BaseException` 포함)에 `~/.orch/hooks.log`에 예외 클래스 이름을 한 줄 남기고 종료 코드 0으로 끝나, 세션 시작이나 알림이 막히지 않게 합니다. 기록 자체가 실패해도 종료 코드는 0입니다.

**`config/settings.json`**

- 훅 네 개와 `permissions.deny`만 둡니다. `deny`는 `~/.orch/secrets/**`에 대한 `Read`, `Grep`, `Glob`, `Edit`, `Write`입니다. pre-bash는 Bash만 보므로, 다른 도구로 그 경로를 읽거나 쓰는 길을 이 규칙이 막습니다.
- 훅 명령은 `PATH`의 `orch`를 부르고 개인 경로를 넣지 않습니다(공개 저장소). pre-bash만 `orch hook pre-bash || exit 2`로 적어, `orch`가 어떤 이유로든 0이나 2가 아닌 코드로 끝나면 차단되게 합니다(Claude Code는 훅 명령을 셸로 실행합니다).
- 레인별 허용 도구 목록은 M16 이관 때 함께 정합니다.
- 실환경 확인에서 `/status`에 설정 오류가 없는지, `/permissions`에 다섯 규칙이 보이는지 확인합니다.

### 5.4 동시성과 원자성

- SQLite는 WAL 모드와 `busy_timeout` 5초로 열고, 상태를 바꾸는 모든 작업은 `BEGIN IMMEDIATE` 트랜잭션으로 묶습니다. 슬롯 판정과 예약이 한 트랜잭션 안에서 일어나므로, 두 세션이 동시에 배분해도 상한을 넘지 않습니다.
- 결과·리뷰 JSON, `TODO.md`는 같은 디렉터리의 임시 파일에 쓴 뒤 `os.replace`로 바꿉니다.
- 같은 작업에 대한 `orch` 명령이 겹치지 않도록, 상태 전이는 "현재 상태가 예상한 값일 때만 바꾼다"(조건부 UPDATE)로 구현합니다. 조건이 맞지 않으면 64로 종료합니다.
- git 작업은 해당 작업의 워크트리 안에서만 실행합니다. 대상 저장소의 기본 작업 트리에서는 `fetch`와 `worktree add/remove`만 실행합니다.

### 5.5 보안과 설정

- 서브 프로세스에는 필요한 환경 변수만 넘깁니다 (`PATH`, `HOME`, 언어 설정, 각 CLI의 설정 경로). 대상 저장소의 `.env`는 읽지 않습니다. GH\_TOKEN·GITHUB\_TOKEN도 서브 환경에서 제거하고, GitHub App 토큰은 orch pr 실행 중에만 발급해 넘깁니다. `github.py`는 토큰을 인자로 받아 `gh` 하위 프로세스의 환경 변수 `GH_TOKEN`으로만 넘기고, 명령줄 인자로 넘기지 않습니다. 예외 메시지와 로그에도 토큰을 넣지 않습니다.
- 사용량 한도 판정은 구조화된 오류를 우선합니다(4.3). 대체 수단인 감지 문구는 `~/.orch/config`의 제공자별 정규식 목록으로 관리해, CLI 메시지가 바뀌면 설정만 고치면 되게 합니다.
- `~/.orch/config`는 TOML 파일이며, 동시 실행 상한, 터미널 백엔드, 알림 설정(`[notify]`, 4.12), 보존 기간, 예약 만료 시간을 둡니다.
- PR 본문, 커밋 메시지, 알림, 리뷰 요약 등 밖으로 나가는 텍스트는 모두 `redact.py`를 거칩니다. 이 모듈은 홈과 `ORCH_HOME` 등을 인자로 받고 `config`를 import하지 않습니다. 경로는 치환한 뒤 개인 경로 패턴(`/Users/`, `/home/`, `C:\Users\`, `/private/tmp/`, `/tmp/claude-`, `/var/folders/`, `/root`)이나, 홈 경로의 `/`를 `-`로 바꾼 인코딩 형태(`str(home).replace("/", "-")`, Claude Code의 scratchpad와 `~/.claude/projects/` 디렉터리 이름 형식)가 남으면 예외를 냅니다. 사용자 이름만으로는 막지 않습니다. 조직 이름 등 공개된 이름과 겹치기 때문입니다. 다음 비밀 정보는 치환하지 않고 항상 예외를 냅니다. 우회 수단은 두지 않습니다.
  - GitHub 토큰: `(?<![A-Za-z0-9_])gh[pousr]_[A-Za-z0-9_.\-]{36,}`, `(?<![A-Za-z0-9_])github_pat_[A-Za-z0-9_.\-]{22,}`
  - JWT: `eyJ[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]*`
  - 개인 키: `-----BEGIN [A-Z ]*PRIVATE KEY-----`
  - 정확한 값 일치: `redact(text, *, home, orch_home, secrets=())`의 `secrets`로 받은 값

## 6. 테스트 전략과 요건서 반영 사항

### 6.1 테스트 전략

실제 Claude·Codex·GitHub 없이 전체 흐름을 검증할 수 있게 세 층으로 나눕니다.

| 층 | 대상 | 방법 |
| --- | --- | --- |
| 단위 | 상태 전이, 슬롯·잠금 판정, glob 겹침, 결과 분류 규칙, 앞머리 파싱 | `pytest`, 임시 SQLite |
| 통합 | prepare → dispatch → run → gate → pr → close 전체 | 임시 git 저장소 + 로컬 bare 저장소를 원격으로 사용, 가짜 에이전트, 가짜 `gh` |
| 실환경 | 실제 Codex·Claude로 샘플 작업 처리 | 샘플 대상 저장소, 1장 "시스템 완료 기준" 검증 |

- 가짜 에이전트(`tests/fake_agents/`)는 시나리오 이름을 받아 정해진 파일을 수정하고 정해진 결과 JSON을 쓰거나, 일부러 실패합니다 (성공, `PARTIAL`, 보고 누락, 시간 초과, 한도 문구 출력, 범위 밖 변경, 테스트 파일 변경, 즉시 종료).
- 가짜 `gh`는 PR 생성 요청을 기록하고, 머지 상태를 테스트가 지정한 값으로 돌려줍니다.
- 가짜 리뷰어는 정해진 판정의 리뷰 JSON을 돌려줍니다 (`PASS`, 구현 쪽 지적의 `BLOCK`, 테스트 쪽 지적의 `BLOCK`).
- 동시성 테스트: 여러 `orch run`을 동시에 끝내 슬롯·잠금 갱신이 꼬이지 않는지, 두 세션이 동시에 배분해도 상한을 넘지 않는지 확인합니다.
