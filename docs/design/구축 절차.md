# 구축 절차

오케스트레이터도, 에이전트용 규칙 파일도 없는 상태에서 Claude Code와 Codex만으로 오케스트레이터를 만들어 가는 절차입니다.

## 1. 출발 조건과 원칙

**출발 조건**: Claude Code(Opus 5.5)와 Codex CLI(GPT-6.1 Sol)는 쓸 수 있지만, `orch`도, `AGENTS.md`·`CLAUDE.md` 같은 하네스도 없습니다. 오케스트레이터를 만드는 일 자체를 에이전트에게 맡겨야 하므로, "도구가 없는 상태에서 그 도구를 만드는" 부트스트랩 문제가 됩니다.

**원칙**

1. **최종 절차를 손으로 먼저 실행합니다.** `orch`가 자동화할 절차(지시서 → 테스트 우선 → Codex 구현 → 게이트 → PR → 머지)를 처음부터 메인이 수동으로 똑같이 따릅니다. 절차 자체를 검증하면서 만들고, 완성된 기능부터 수동 단계를 하나씩 대체합니다.
2. **처음부터 최종 경로 구조를 씁니다.** 지시서·결과·로그·워크트리를 처음부터 `~/.orch/orchestrator/` 아래 최종 위치에 둡니다. `orch`가 완성되면 별도 이관 없이 그대로 이어받습니다.
3. **하네스는 최소로 시작해 키웁니다.** 처음 하네스는 "설계 문서가 어디 있고 무엇을 지켜야 하는지"만 담고, 실제로 문제가 생긴 규칙만 추가합니다.
4. **운영본과 개발본을 분리합니다.** `orch`로 `orch`를 개발하는 단계부터는, 실행에 쓰는 설치본과 수정 중인 저장소를 반드시 분리합니다.
5. **단계마다 종료 조건을 둡니다.** 종료 조건을 사용자가 확인한 뒤에만 다음 단계로 넘어갑니다.

**전체 단계**

| 단계 | 목표 | 주요 산출물 | 종료 조건 | 주 수행자 |
| --- | --- | --- | --- | --- |
| Phase 0 | 환경 준비 | 설치·인증된 도구, GitHub 허브 저장소 | 환경 점검 체크리스트 전부 통과 | 사용자 |
| Phase 1 | 최소 하네스 | `AGENTS.md`, `CLAUDE.md`, 설계 문서 사본, 템플릿, 수동 게이트 스크립트, 서브에이전트 정의 | 사용자 검토 후 main에 머지 | 메인(초안) + 사용자(검토) |
| Phase 2 | 수동 오케스트레이션으로 핵심부 구현 | `orch` 최소 기능(MVP) | 가짜 에이전트로 prepare → run → gate → pr → close 통합 테스트 통과 | 메인(분해·테스트·판정) + Codex(구현) |
| Phase 3 | 자기 적용 | 나머지 기능(머지 대기, H2 실행, 훅, doctor, launchd, 정리) | 허브 저장소 자체를 `orch`로 개발해 PR 3건 이상 생성 | `orch` 경유 |
| Phase 4 | 실환경 검증 | 샘플 대상 저장소, 장애·재부팅 시험 결과 | 요건 1장 "시스템 완료 기준" 충족 | `orch` 경유 + 사용자 |
| Phase 5 | 운영 전환 | 실제 대상 등록, 상시 가동 | 1주 무인 운용 중 미처리 장애 없음 | 사용자 |

## 2. Phase 0 환경 준비, Phase 1 최소 하네스

- [x] Claude Code 설치와 버전 고정, Pro 로그인, `/model`에서 Opus 5.5 선택 확인

- [x] 맥에서 개인 GitHub 자격 증명 제거, `2muni-labs` 조직에 GitHub App 생성·설치, 토큰 스크립트와 git 자격 증명 도우미, 봇 커밋 신원 설정 (실행 설계 6장 "GitHub 인증 구성")

- [x] 맥 잠자기 비활성화 (개발 중 세션 유지용)
- [x] GitHub에 공개 허브 저장소 `orchestrator` 생성, 봇 토큰으로 클론 성공
- [x] main 규칙 세트 적용과 실제 차단 확인 (PR 필수, 승인 1건, force push·삭제 금지). 저장소를 공개로 전환해 무료 조직에서 적용
- [x] 맥에 저장소 복제 (예: `~/work/orchestrator`), 런타임 디렉터리 `~/.orch/orchestrator/{tasks,results,reviews,logs,worktrees}` 생성

### Phase 1 — 최소 하네스

허브 저장소에 에이전트가 읽을 규칙과 설계 문서를 넣는 단계입니다. 아직 Codex에 맡길 지시서 체계가 없으므로, 이 단계만은 **메인(Claude Code)이 직접 작성하고 사용자가 검토**합니다. 하네스는 설계 산출물이므로 메인의 구현 금지 원칙과 충돌하지 않습니다.

| 파일 | 내용 | 읽는 주체 |
| --- | --- | --- |
| `docs/design/*.md` | 이 문서의 요건·실행 설계·기술 설계·구축 절차 탭을 Markdown으로 내보낸 사본 | 모두 |
| `AGENTS.md` | 프로젝트 목적, 설계 문서 위치와 우선순위, 기술 규약(Python 3.14, 런타임은 표준 라이브러리만, 타입 힌트, pytest), 디렉터리 구조, 테스트 우선과 테스트 파일 수정 금지, 수정 범위 준수, 결과 JSON 작성 의무와 경로, 금지 사항(push·머지·명령의 백그라운드 실행·런타임 의존성 추가), 커밋 메시지는 영어 | Codex(자동으로 읽음), Claude |
| `CLAUDE.md` | `AGENTS.md`를 가져오고, 메인 전용 규칙(역할 경계, 수동 절차 요약, 사용자 보고는 한국어)을 추가 | 메인 |
| `templates/task.md` | TOML 앞머리 지시서 템플릿 | 메인 |
| `schemas/result.json`, `schemas/review.json` | 결과·리뷰 형식 (요건 7장) | 메인, 서브 |
| `.claude/agents/orch-explorer.md`, `orch-reviewer.md` | 읽기 전용 탐색·리뷰 서브에이전트 | 메인 |
| `scripts/gate.sh` | 수동 G1\~G3: 변경 파일과 수정 범위 대조, `pytest`, `ruff` | 메인 |
| `scripts/run-sub.sh` | 수동 서브 실행 (Phase 2에서 추가, M6 전까지 사용): 시간 상한, 토큰 제거, 결과 파일 검증과 이동 | 메인 |
| `pyproject.toml` | 빈 패키지 골격. `pytest`, `ruff`는 개발 전용 의존성 | 모두 |
| `.github/pull_request_template.md` | 영어 PR 본문 구조 (요약, 변경 파일, 게이트 결과, 리뷰 판정) | 메인 |

**진행 순서**

1. 사용자가 이 문서를 Markdown으로 내보내 `docs/design/`에 넣습니다.
2. 사용자가 허브 저장소에서 tmux 세션을 열고 Claude Code(Opus 5.5)를 실행합니다.
3. 메인이 설계 문서를 읽고 위 파일 초안을 `task/harness-v0` 브랜치에 작성합니다. 지시서 템플릿은 실제 첫 작업에 써 보며 다듬습니다.
4. 메인이 PR을 만들고, 요건 정의 9장의 머지 정책에 따라 사용자 또는 검증 세션이 머지합니다.

**종료 조건**: Codex가 `AGENTS.md`를 읽고 규칙을 요약할 수 있는지 `codex exec`로 한 번 확인하고, Claude Code에서 두 서브에이전트가 목록에 나타나는지 확인합니다. 또한 임시 워크트리에서 `codex exec --sandbox workspace-write`로 (a) 워크트리 안 파일 수정, (b) `git commit`, (c) 워크트리 밖 결과 파일 쓰기, (d) `uv run pytest` 실행의 성공 여부를 확인해 보고합니다. 저장소 `.git` 전체에 쓰기를 여는 `--add-dir`은 쓰지 않습니다. 메인, `orch-explorer`, `orch-reviewer`가 워크트리와 `reviews` 디렉터리를 권한 요청 없이 읽을 수 있는지도 확인합니다.

**실험 결과와 결정** (codex-cli 0.160.0): (a) 성공, (b)·(c)·(d) 실패. 메인이 미리 `uv sync --frozen`을 실행하면 서브의 `.venv/bin/python -m pytest`는 `--basetemp` 없이 성공합니다. 이에 따라 다음과 같이 정합니다.

- 서브는 커밋하지 않고 파일만 수정하며, 결과 JSON은 워크트리 안 `.orch-result.json`(gitignore 대상, G1 제외)에 씁니다. 결과 파일 이동과 커밋은 메인이 수행합니다.
- 메인이 워크트리 생성 직후 샌드박스 밖에서 `uv sync --frozen`을 실행합니다. `verify`는 네트워크 없이, 워크트리 밖에 쓰지 않고 동작해야 합니다.
- 메인과 두 서브에이전트는 기본 상태에서 워크트리와 `reviews`를 읽지 못합니다. 사용자 설정 `~/.claude/settings.json`의 `permissions.additionalDirectories`에 `~/.orch/orchestrator`를 등록하며, 클론별 설정은 필요 없습니다.

## 3. Phase 2 — 수동 오케스트레이션으로 핵심부 구현

`orch`가 없으므로 메인(Claude Code)이 `orch`가 할 일을 셸 명령으로 직접 수행합니다. 절차는 요건서의 최종 절차와 같고, 도구만 수동입니다.

### 3.1 작업 하나의 수동 절차

| 단계 | 수행자 | 내용 |
| --- | --- | --- |
| 0. 계획 | 메인 → 사용자 승인 | 기술 설계 기준으로 모듈을 작업 단위로 분해하고, 작업 목록(id, 목적, 등급, 레인, 수정 범위, 선행 작업)을 보고. 사용자가 승인 |
| 1. 준비 | 메인 | `git fetch origin` 후 `git worktree add ~/.orch/orchestrator/worktrees/<id> -b task/<id> origin/main`, 이어서 워크트리에서 `uv sync --frozen` |
| 2. 테스트 우선 | 메인 | 워크트리에 테스트와 인터페이스 스텁(본문은 `raise NotImplementedError`)을 작성하고, 구현 대상 테스트가 실패하는 것을 확인한 뒤 첫 커밋. 스텁만으로 통과하는 테스트는 그 이유를 커밋 메시지에 적음. 스텁 파일은 수정 범위에 포함 |
| 3. 지시서 | 메인 | 템플릿으로 `~/.orch/orchestrator/tasks/<id>.md` 작성 (확정 사실, 수정 범위, 검증 명령, 결과 JSON 경로) |
| 4. 실행 | 메인 | 백그라운드 셸로 `scripts/run-sub.sh <id>` 실행 (M6 전까지 쓰는 임시 도구. 앞머리의 모델·강도·시간 상한으로 `codex exec`를 실행하고, 결과 파일을 옮기며, 없거나 형식이 틀리면 로그 끝의 한도 문구에 따라 `BLOCKED_QUOTA` 또는 `FAILED`로 대신 기록). 배분 내용을 보고하고 턴 종료 |
| 5. 판정 | 메인 | 완료 알림을 받으면 `results/<id>.json` 확인 (`report_missing`이면 재시도 전에 로그를 확인해 한도 오류 여부를 판단) → `scripts/gate.sh <id>` → 통과하면 서브의 변경을 커밋 → L3 이상이면 diff를 `reviews/<id>.diff`로 저장하고 경로를 넘겨 `orch-reviewer`로 교차 리뷰 |
| 6. PR | 메인 | 통과 시 `origin/main` 기준 rebase, 테스트 재실행, `git push -u origin task/<id>`, `gh pr create`(영어). 사용자에게 보고 |
| 7. 머지 | 사용자 또는 검증 세션 → 메인 | 요건 정의 9장의 머지 정책에 따라 머지되면 메인이 워크트리와 로컬 브랜치 정리 |
| 8. 실패 처리 | 메인 | 1회 재시도(테스트 커밋으로 되돌리고 `.orch-result.json`을 지운 뒤 실패 요약 추가). 다시 실패하면 폐기하고 재분해 |

- 동시 실행은 **1\~2개**로 제한합니다. 잠금 기능이 없으므로 작업 목록에서 수정 범위가 겹치지 않는지 메인이 확인합니다.
- Codex 사용량이 부족하면 4단계를 `claude -p --model claude-sonnet-5-5`로 바꿔 실행합니다(C 레인 수동판).
- 이 단계에서 지시서 템플릿, 결과 JSON 규격, 게이트 스크립트의 불편한 점이 드러나면 하네스를 PR로 고칩니다. 이 기록이 `orch` 설계의 검증 자료가 됩니다.

### 3.2 모듈 구현 순서

기술 설계의 패키지 구조를 의존 관계 순으로 나눴습니다. 같은 묶음 안의 작업은 수정 경로가 겹치지 않으므로 병렬로 진행할 수 있습니다. 묶음 2는 M2 `redact`와 M2 `config`·`taskfile`을 먼저 병렬로 진행하고, 둘이 머지된 뒤 M3와 M4를 병렬로 진행합니다.

| 묶음 | 모듈 | 내용 | 선행 | 예상 등급 |
| --- | --- | --- | --- | --- |
| 1 | M1 `models`, `store` | 데이터클래스, 상태 열거형, 전이 표, SQLite 스키마와 마이그레이션, 조건부 상태 전이. `m1-models` 후 `m1-store` 순서로 나눠 진행 | — | L2 (`models`), L3 (`store`) |
| 2 | M2 `redact` | 밖으로 나가는 텍스트의 개인 경로 치환과 토큰·잔여 경로 차단 (`config`를 import하지 않음) | — | L3R |
| 2 | M2 `config`, `taskfile` | `ORCH_HOME` 기준 경로 계산, `targets.toml`, `~/.orch/config`, TOML 앞머리 파싱과 검증 | M1 | L2 |
| 2 | M3 `gitops` | worktree 생성·제거, diff, rebase, push 래퍼. 커밋 메시지에 `redact` 적용 | M2 | L2 |
| 2 | M4 `results`, 가짜 에이전트 | 결과·리뷰 스키마 검증, 대체 기록, 장애 시나리오별 가짜 에이전트 | M1 | L2 |
| 3 | M5 `store` 추가분 | 스키마 v2 `pushed_sha`, `pr_open` → `conflict`, 실행·잠금·게이트 기록 헬퍼 | M1 | L3 |
| 3 | M3 `gitops` 추가분 | 임시 병합과 중단, 임시 병합을 건너뛴 작업 커밋 판별 | M3 | L2 |
| 3 | M5 `scheduler` | 슬롯 예약과 만료, glob 겹침 잠금, 의존 판정, `next` | M1, M2, M5 `store` | L3 |
| 3 | M7 `gate` | G1 범위, G2 테스트, G3 정적 검사 | M3 추가분, M5 `store` | L2 (위험 영역으로 리뷰) |

**묶음 3 범위 밖**: `ghapp.py`는 MVP 이후 백로그입니다. MVP의 토큰 발급은 `~/.orch/bin/ghapp-token.sh`를 호출합니다. `TODO.md` 생성은 M11, 새 배분 중단 플래그는 M15에서 추가합니다.

**M10 필수 시나리오**: 가짜 리뷰어의 `BLOCK` 경로를 검증합니다. 이 경로는 코드로 실행된 적이 없습니다.

- 재시도 경로: 구현 쪽 P0·P1로 `BLOCK` → `reviewing` → `judging` → `orch retry` → 재실행 → 통과 → `ready`. 2회차의 `BLOCK`은 `orch discard`로 끝납니다.
- 폐기 경로: 테스트 쪽 P0·P1로 `BLOCK` → `reviewing` → `judging` → 재시도 없이 `orch discard`. 이 작업을 기다리던 작업은 `blocked`가 됩니다.
- 넘김 경로: `BLOCK` → `orch review save --triage` → `ready` → `orch pr`. PR 본문 맨 위의 `Review BLOCK overridden` 섹션과 `review-overridden` 라벨을 확인합니다. 처리하지 않은 P0·P1이 있거나, `tests/` 밖 지적에 `insufficient_tests`를 썼거나, 후속 작업이 등록되지 않은 triage는 거부됩니다. 저장소에 라벨이 없으면 `orch pr`이 PR을 만들지 않고 오류로 멈춥니다.

**M9 필수 조건**: `targets.toml`은 공개 저장소인 허브에 커밋되므로 개인 경로가 들어가면 안 됩니다. `orch target add`는 `path`를 홈 기준 `~/` 형태로만 저장하고, 홈 밖의 경로는 거부합니다.

**MVP 정의**: `target add`, `prepare`, `dispatch`, `next`, `run`, `gate`, `review save`, `pr`, `update`, `close`, `discard`, `retry`, `resume`, `status`가 동작하고, M10 통합 테스트가 통과한 상태입니다. 훅, H2 실행, 상시 운용 기능은 MVP에 넣지 않습니다.

**사용량 관리**: 메인(Opus 5.5)은 분해, 테스트 작성, 판정에만 쓰고 구현은 Codex에 맡깁니다. Claude Pro 한도는 claude.ai 채팅과 공유하므로, 구현 기간에는 채팅 사용을 줄입니다.

## 4. Phase 3 자기 적용, Phase 4·5 검증과 운영 전환

### 4.1 Phase 3 — orch로 orch를 개발

MVP가 머지되면 허브 저장소 자체를 대상으로 등록하고, 남은 기능은 `orch`를 거쳐 개발합니다. 이때부터 수동 절차의 각 단계가 `orch` 명령으로 바뀝니다.

**운영본과 개발본 분리 규칙**

- **운영본**: main의 태그(예: `v0.1.0`)를 `uv tool install`로 설치한 `orch`. 메인과 백그라운드 작업은 항상 이것만 실행합니다.
- **개발본**: 허브 저장소와 그 워크트리. 여기서 수정된 코드는 PR이 머지되고 새 태그가 붙기 전까지 실행에 쓰지 않습니다.
- **갱신 절차**: 사용자가 승인하면 `orch status`로 실행 중인 작업이 없는지 확인 → `~/.orch/state.db` 백업 → `uv tool install --reinstall`로 새 태그 설치 → 스키마 마이그레이션은 앞으로만 진행합니다.
