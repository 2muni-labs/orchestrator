# 실행 설계 (하이브리드 레인)

요건서 본문의 3장과 10장을 구현하는 상세 설계입니다. 오케스트레이션 로직은 Claude Code 기본 기능과 셸 스크립트만으로 동작하고, 터미널(Tern 또는 tmux)은 세션 유지와 관찰 화면만 담당합니다.

## 1. 원칙과 레인

서브 실행 경로는 네 개의 레인으로 고정하고, 모든 레인의 완료는 "백그라운드 셸 명령 또는 백그라운드 서브에이전트가 끝나면 메인 턴이 열린다"는 Claude Code 기본 동작 하나로 통지합니다.

**설계 원칙**

1. 메인은 작업마다 레인 하나를 고르고, 셸 명령을 직접 조합하지 않고 `orch` CLI만 호출합니다.
2. 코드를 수정하는 작업은 반드시 로그가 남는 레인(B·C·D)으로 보냅니다. A 레인은 읽기 전용입니다.
3. 판정은 항상 결과 JSON과 게이트로 합니다. 완료 알림의 종료 코드나 화면 출력으로 판정하지 않습니다.
4. Codex MCP 직접 호출은 쓰지 않습니다. 동기 호출이라 Codex가 끝날 때까지 메인 턴을 묶기 때문입니다.

**레인 정의**

| 레인 | 실행 수단 | 용도 | 수정 권한 | 완료 통지 | 관찰 |
| --- | --- | --- | --- | --- | --- |
| A | Claude 내장 서브에이전트 (백그라운드) | 탐색, 리뷰, 사실 확인 | 없음 | 서브에이전트 완료 알림 | 메인 화면 + 요약 로그 |
| B | 백그라운드 셸의 `orch run` → `codex exec` | Codex 구현 (기본 구현 레인) | 수정 범위 내 | 백그라운드 명령 종료 알림 | 로그 패널 |
| C | 백그라운드 셸의 `orch run` → `claude -p` | Claude 구현 (대체 모델, Codex 부족, Claude 지정) | 수정 범위 내 | 백그라운드 명령 종료 알림 | 로그 패널 |
| D | 대화형 패널 + 백그라운드 셸의 `orch wait` | 실행 중 개입이 필요한 예외 작업 | 수정 범위 내 | `orch wait` 종료 알림 | 해당 패널에서 직접 대화 |

D 레인의 대화형 패널은 스스로 메인을 깨울 수 없으므로, 메인이 `orch wait <id>`를 백그라운드 셸로 걸어 둡니다. 서브가 결과 JSON을 쓰는 순간 이 명령이 끝나 메인 턴이 열립니다.

**레인 선택 규칙** (위에서부터 판정, 처음 맞는 레인 사용)

| 순서 | 조건 | 레인 |
| --- | --- | --- |
| 1 | 코드 수정이 없음 (탐색, 리뷰, 조사) | A |
| 2 | 사용자가 "개입하며 진행"을 지정했거나, 시행착오가 예상되는 시제품 작업 | D |
| 3 | 매핑표상 구현 담당이 Codex이고 Codex 잔여 사용량이 충분함 | B |
| 4 | 그 외 구현 작업 | C |

- L4 작업은 어느 레인에도 보내지 않고 메인이 다시 분해합니다.
- 리뷰(G4)는 구현과 다른 제공자가 맡습니다. Codex 구현은 Claude `reviewer` 서브에이전트(A)가, Claude 구현은 읽기 전용 샌드박스의 `codex exec`(B)가 리뷰합니다.

## 2. 디렉터리 구조와 orch CLI

작업 상태는 모두 파일로 남깁니다. 메인 세션이 끊겨도 이 파일들로 상태를 복원할 수 있어야 하기 때문입니다.

```
orchestrator/                 # 허브 저장소 (GitHub)
├── pyproject.toml            # uv 패키지, orch 엔트리포인트
├── src/orch/                 # CLI, 상태 저장소, 레인 실행기, 게이트, 터미널 어댑터
├── config/
│   ├── main.md               # 메인 규칙 (M16부터 orch open 시 주입)
│   ├── settings.json         # 훅, ~/.orch/secrets 접근 금지 (orch open 시 주입, 기술 설계 5.3)
│   └── agents/               # orch-explorer, orch-reviewer 정의 (M16)
├── templates/                # 지시서, PR 본문 템플릿
├── schemas/                  # 결과·리뷰 JSON 스키마
├── tests/fake_agents/        # 가짜 codex·claude (테스트 모드)
└── targets.toml              # 등록된 대상 저장소

~/.orch/                      # 런타임 데이터 (커밋하지 않음)
├── state.db                  # SQLite: 작업 상태, 잠금, 실행 슬롯, 실행 기록 (모든 대상 공통)
├── config                    # TOML: terminal_backend, 동시 실행 상한, [gate] timeout_min
└── <대상>/
    ├── tasks/<id>.md         # 지시서
    ├── results/<id>.json     # 결과 보고 (워크트리의 .orch-result.json을 옮긴 것)
    ├── reviews/<id>.json     # 리뷰 결과
    ├── logs/<id>.<n>.log     # 서브 실행 로그 (n번째 실행, 실행마다 새 파일)
    ├── logs/subagents.log    # A 레인 요약 로그
    ├── TODO.md               # state.db에서 자동 생성. 저장소 작업 트리에는 만들지 않음
    └── worktrees/<id>/       # git worktree (브랜치 task/<id>)
```

대상 저장소 안에는 아무것도 만들지 않습니다. git worktree는 저장소 밖에도 둘 수 있으므로 `.gitignore` 수정도 필요 없습니다. 서브의 결과 파일 `.orch-result.json`은 서브가 끝난 직후 `orch`가 `results/`로 옮기고 G1 검사에서도 제외하므로 커밋에 들어가지 않습니다. `setup_command`가 만드는 파일(`.venv/` 등)은 대상 저장소가 이미 무시하고 있어야 합니다.

**orch 명령**

| 명령 | 동작 | 호출 주체·방식 |
| --- | --- | --- |
| `orch target add <경로> --name <대상>` | 대상 등록 (GitHub 저장소, 기본 브랜치, 사전 준비·테스트·린트 명령, 공유 파일 목록). 허브의 `targets.toml`만 고치며, 커밋은 PR로 함. 사용자는 대상 저장소에 `review-overridden` 라벨을 한 번 만들어 둠 (기술 설계 4.7) | 사용자 |
| `orch open <대상>` | 메인 Claude Code를 대상 위치에서 실행하고 허브 설정을 주입 (6장, 기술 설계 5.2) | 사용자 |
| `orch hook <이름>` | `session-start`, `pre-bash`, `subagent-stop`, `notification` 훅 처리 (기술 설계 5.3) | Claude Code 훅 |
| `orch prepare <지시서>` | 지시서 검증, 브랜치·워크트리 생성, `setup_command` 실행. 메인이 여기에 테스트와 인터페이스 스텁을 커밋 | 메인, 일반 셸 |
| `orch dispatch <id>` | 테스트 커밋 확인 후 잠금·의존·슬롯 판정. 충족 시 슬롯 예약(`reserved`, 10분 만료), 아니면 `queued` | 메인, 일반 셸 (즉시 종료) |
| `orch next` | `queued` 작업을 다시 판정해 새로 예약된 목록 반환. 완료 알림마다 호출 | 메인, 일반 셸 |
| `orch run <id>` | B·C 레인 실행, 시간 상한 강제, 결과 분류 후 종료 | 메인, **백그라운드 셸** |
| `orch wait <id>` | D 레인. 결과 JSON 생성 또는 시간 상한까지 대기 | 메인, **백그라운드 셸** |
| `orch wait <id> --merged [--interval <초>] [--max-wait <분>]` | PR이 머지될 때까지 대기(기본 60초 간격, 상한 90분). 머지되면 0, 머지 없이 닫히면 50, 상한에 도달하면 60 (기술 설계 4.7.2) | 메인, **백그라운드 셸** |
| `orch gate <id>` | G1 범위(테스트 파일 변경 포함), G2 테스트, G3 정적 검사 실행 후 JSON 출력 | 메인, 일반 셸 |
| `orch review <id> --by codex` | Claude 구현분을 Codex로 리뷰하고 결과 저장 | 메인, **백그라운드 셸** |
| `orch review save <id> [--triage <파일>]` | `orch-reviewer` 서브에이전트의 리뷰 JSON을 표준 입력으로 받아 검증·저장. `--triage`는 `BLOCK`을 분류해 `ready`로 넘김 (기술 설계 4.6) | 메인, 일반 셸 |
| `orch retry <id>` | 1회 재시도. 워크트리를 테스트 커밋으로 되돌리고 실패 요약을 덧붙여 슬롯 재예약 | 메인, 일반 셸 |
| `orch resume <id> [--keep]` | `blocked`·`orphaned` 작업 재개. 기본은 테스트 커밋으로 되돌림. `attempt`를 소모하지 않음 | 메인, 사용자 승인 후 |
| `orch pr <id>` | `origin/main` 기준 rebase, G2 재실행, 작업 브랜치 push, PR 생성 (영어, 템플릿 사용) | 메인, 일반 셸 |
| `orch update <id>` | 열린 PR을 최신 main과 임시로 합쳐 게이트 실행. 충돌이 없으면 push하지 않고 임시 결과를 버림. 충돌이 있으면 `conflict`로 전환 (기술 설계 4.7.1) | 메인, 일반 셸 |
| `orch close <id>` | PR 머지 여부를 확인한 뒤 워크트리·잠금 정리. 미머지면 거부 | 사용자 또는 메인 |
| `orch discard <id>` | 작업 폐기, 잠금 해제 | 메인, 일반 셸 |
| `orch kill <id>` | 실행 중단, `FAILED`(aborted) 기록, 워크트리 보존 | 메인 또는 사용자 |
| `orch status` | 전체 작업 상태 요약 | 메인, 훅, 사용자 |
| `orch watch [--panels]` | 작업 상태판을 앞단에서 갱신 (기술 설계 4.11). `--panels`는 실행 중인 작업의 로그 패널을 열고 닫음 (M13) | 사용자, `orch open` |
| `orch gc [--dry-run]` | 보존 기간이 지난 `closed`·`discarded` 작업의 로그·결과·리뷰 정리, `git worktree prune` (기술 설계 4.10.1) | launchd 하루 1회, `doctor`, 사용자 |

작업 상태의 원본은 `state.db` 하나이며, 상태 목록과 전이 규칙은 기술 설계 탭 3장의 상태 머신을 따릅니다.

**운영 명령** (상시 운용용)

| 명령 | 동작 | 호출 주체·방식 |
| --- | --- | --- |
| `orch doctor` | 메인 세션 생존, Claude Code·Codex 인증, GitHub App 토큰 발급, 디스크 여유, Tailscale 연결, 멈춘 작업 점검. 나빠진 항목만 알림, 인증·디스크 장애면 새 배분 중단, 멈춘 작업은 kill 후 알림. 메인 세션은 재기동하지 않음 (기술 설계 4.10) | launchd 10분 주기, 사용자 |
| `orch service install` / `uninstall` | launchd 에이전트 설치와 제거 (6장 상시 운용 구성, 기술 설계 4.10.2) | 사용자, 최초 1회 |
| `orch service restore` | 터미널 기록이 있는 대상 중 `orch-<대상>` 세션이 없는 대상만 `orch open --no-attach`로 엶 | launchd 로그인 시 |

**orch run 내부 처리 순서**

1. 레인에 맞는 명령으로 서브 실행 (3장 템플릿)
2. 출력을 이번 실행의 `logs/<id>.<n>.log`에 기록
3. 강제 종료 신호(메모리 정리, 시간 초과)로 끝났으면 `FAILED`(강제 종료 또는 시간 초과)로 기록
4. 종료 후 워크트리의 `.orch-result.json`을 `results/<id>.json`으로 옮기고 스키마로 검증. 유효하면 그 값을 따름
5. 유효한 결과가 없으면 구조화된 오류, 이어서 한도 문구로 판정해 `BLOCKED_QUOTA`로 기록하고, 아니면 `FAILED`(보고 누락)로 대신 작성 (기술 설계 4.3)
6. `state.db` 갱신 후 종료 → 이 종료가 메인의 새 턴을 엶. 결과가 `BLOCKED`·`BLOCKED_QUOTA`이면 종료 전에 `blocked`로 옮김

종료 코드는 상태별로 나누지만(0 완료, 10 부분 완료, 20 실패, 30 중단, 40 한도), 완료 알림에 종료 코드가 틀리게 표시되는 사례가 보고되어 있으므로 메인은 결과 JSON으로만 판정합니다.

## 3. 실행 템플릿, 메인 규칙, 훅

아래 플래그는 설치된 버전의 `--help`로 최종 확인한 뒤 확정합니다. 시간 상한은 `orch run`이 프로세스 그룹 단위로 직접 강제하므로, 템플릿에는 시간 상한 명령이 없습니다.

**B 레인 (Codex 구현)**

```bash
# D=~/.orch/<대상>, W=$D/worktrees/<id>. 모델은 CLI 기본값에 의존하지 않고 항상 명시
codex exec --json \
  --disable hooks --disable plugins \
  -C "$W" \
  -m gpt-6.1-sol -c model_reasoning_effort=<low|medium|high|xhigh> \
  --sandbox workspace-write \
  - < "$D/tasks/<id>.md" \
  > "$D/logs/<id>.<n>.log" 2>&1
```

- 강도: L1 `low`, L2 `medium`, L3 `high`, L3 위험 영역 `xhigh`. `max`·`ultra`는 쓰지 않습니다.
- Claude 구현분 리뷰는 같은 명령에 `--sandbox read-only`와 `-o <마지막 메시지 파일>`을 붙여 실행합니다(기술 설계 4.6).
- `--disable hooks --disable plugins`는 사용자의 전역 Codex 설정(`~/.codex/hooks.json`의 훅, 플러그인이 띄우는 MCP 서버)이 서브 실행에 섞이지 않게 합니다. codex-cli 0.160.0 실측(2026-11-07): 기본 설정에서는 실행마다 훅이 돌고 MCP 서버가 떴으나, 두 인자를 붙이면 읽기 전용 리뷰 형태와 `workspace-write` 형태 모두 3회씩 훅과 MCP가 없었고 종료 코드와 결과는 같았습니다. 전용 `CODEX_HOME`(빈 설정 + 인증 링크)은 두 번째 실행부터 플러그인 MCP가 다시 떠서 쓰지 않습니다. `CODEX_HOME`은 그대로라 rollout 파일과 한도 판정은 바뀌지 않습니다. 알 수 없는 기능 이름도 거부되지 않으므로, Codex 버전을 올릴 때 다시 측정합니다.
- `workspace-write` 샌드박스 실험 결과(codex-cli 0.160.0): 워크트리 안 파일 수정과 `.venv/bin/python -m pytest`는 성공하고, `git commit`, 워크트리 밖 쓰기, `uv run`은 실패합니다. 그래서 `--add-dir`을 쓰지 않고, 서브는 파일만 수정합니다. 사전 준비, 결과 파일 이동, 커밋은 샌드박스 밖에서 합니다.
- `--json`은 `thread_id`를 얻어 한도 판정의 구조화된 오류를 찾는 데 씁니다(기술 설계 4.3). 로그가 JSONL이 되고 지시서가 출력되지 않습니다. 도구 호출은 이벤트에 나오지 않을 때가 있으므로(code mode), 이벤트로 실행 여부를 판단하지 않습니다.
- `workspace-write` 샌드박스 프로세스 제어 실험 결과(codex-cli 0.160.0): `start_new_session`, `os.killpg`, SIGTERM·SIGKILL의 그룹 전달은 성공하고, `ps`는 setuid 실행 금지로 실패합니다(`Operation not permitted`). `orch run`은 샌드박스 밖에서 실행되므로 `ps`를 그대로 씁니다. 다만 서브의 `verify`는 샌드박스 안에서 돌므로, 실제 `ps`가 필요한 테스트는 `PermissionError`일 때만 건너뛰고 샌드박스 밖의 G2에서 검증합니다.
- 구축 전 확인: `codex --version`(0.159.1 이상), `codex debug models | grep gpt-6.1-sol`, `codex exec -m gpt-6.1-sol "Say hi in one word"`.

```markdown
- 작업 브랜치의 첫 커밋으로 테스트와 인터페이스 스텁을 넣은 뒤 배분한다. 스텁 파일은 수정 범위에 포함한다.

```

**지시서 공통 문구 (서브용)**: "커밋하지 않는다." 커밋은 게이트 통과 후 샌드박스 밖에서 합니다. "명령을 백그라운드로 보내지 않는다." 서브 안에서 다시 백그라운드 명령을 띄우면 미완료 보고가 먼저 오고 실제 결과가 나중에 오는 이중 보고가 생기기 때문입니다.

**훅 구성**

| 훅 | 동작 | 목적 |
| --- | --- | --- |
| SessionStart | `orch status`를 메인 컨텍스트에 주입. `running`인데 프로세스가 없는 작업은 `orphaned`로 표시 | 메인 재시작 후 상태 복원 |
| SubagentStop | A 레인 서브에이전트의 최종 응답 요약을 `logs/subagents.log`에 추가 | A 레인 관찰 가능성 |
| PreToolUse (Bash) | `codex`, `claude -p`를 `orch` 없이 직접 실행하거나, git push --force·git push --force-with-lease·gh pr merge·`gh api`의 PR 머지 경로를 실행하거나, `~/.orch/secrets/`에 닿으면 차단. `orch resume`은 사용자 확인 (브랜치 갱신은 `orch` 안에서만 수행, 기술 설계 5.3) | 레인 우회 방지 |
| Notification (matcher `permission_prompt`) | 권한 요청 알림이면 ntfy로 `input_wait`를 보냄. 창이 뜬 뒤 약 6초 동안 응답이 없을 때만 불림 (기술 설계 4.12) | 입력 대기를 휴대폰으로 알림 |

백그라운드 서브에이전트의 권한 요청은 메인 세션으로 올라오므로, 레인별 허용 도구 목록을 미리 설정해 승인 요청이 쌓이지 않게 합니다. 훅과 허용 도구는 모두 허브의 config/settings.json에 두고, orch open이 실행 옵션으로 주입합니다. M14는 훅과 `~/.orch/secrets/` 접근 금지(`permissions.deny`)만 두고, 허용 도구 목록은 M16에서 정합니다. 훅은 `orch open` 없이 실행한 세션에는 걸리지 않으며, 이것이 훅이 잘못됐을 때의 탈출구입니다(기술 설계 5.2).

## 4. 관찰 화면과 터미널 계층

오케스트레이션 로직은 Tern에 의존하지 않습니다. 터미널은 세션 유지, 원격 접속, 관찰 화면만 담당하며, `orch` 안의 터미널 어댑터로 분리해 Tern과 tmux를 설정 한 줄로 바꿀 수 있게 합니다. **터미널 백엔드는 tmux만 사용**하고, Tern 재평가(아래) 결과, M13에는 tern 어댑터를 넣지 않고 Tern은 터미널·원격 접속 역할로만 시범 평가를 이어 갑니다. Herdr는 1차 구축 이후 재검토합니다. 아래 표는 tmux와 Tern의 역할 비교입니다.

**터미널 어댑터**

- `~/.orch/config`(TOML)의 `terminal_backend`로 선택합니다. 지금 값은 `tmux`뿐입니다. `tern`은 시범 평가가 끝나고 사용자가 채택을 결정하면 별도 작업으로 추가하며, 그때까지 어댑터 경계는 아래 세 함수로 유지합니다.
- M13의 관찰 패널 구성과 D 레인은 `terminal_split`, `terminal_send`, `terminal_open_tab` 세 함수만 호출합니다. M11의 `orch watch` 상태판은 터미널 기능을 쓰지 않습니다. 나머지 `orch` 명령은 터미널 기능을 쓰지 않습니다.
- 메인 Claude Code는 반드시 이 터미널 세션 안에서 실행합니다. 백그라운드 작업이 메인 프로세스에 묶여 있으므로, 창이나 원격 연결이 끊겨도 세션이 살아 있어야 합니다.
- `terminal_send`는 어댑터가 만들어 기록한 창·패널에만 보내고, 메인 패널에는 보내지 않습니다(기술 설계 5.2).

**화면 배치**

```
┌─────────────────────────┬──────────────────────────┐
│ 메인: Claude Code (대화) │ orch watch: 작업 상태판     │
│                         ├──────────────────────────┤
│                         │ tail -f logs/<id>.<n>.log│
├─────────────────────────┼──────────────────────────┤
│ (메인)                   │ tail -F logs/subagents.log│
└─────────────────────────┴──────────────────────────┘
```

**Tern 의존 부분과 tmux 대체**

| Tern 역할 | tmux 대체 | 잃는 것 |
| --- | --- | --- |
| 메인 세션 유지 | tmux 세션 안에서 실행 (detach 후에도 유지) | 재부팅 후 자동 복원 (tmux-resurrect로 일부 보완) |
| Windows·모바일 원격 접속 | Tailscale SSH 접속 후 `tmux attach` | 앱 수준의 호스트 관리, 브라우저·모바일 전용 클라이언트 |
| 로그 패널 배치 | `tmux split-window`로 `tail -f` 패널 생성 | 네이티브 렌더링, 패널 고정 등 편의 기능 |
| D 레인 대화형 패널 | `tmux new-window` + `send-keys` | 거의 없음 |
| 입력 대기 알림 | Tern의 평가 범위에서 제외. ntfy가 맡음 (기술 설계 4.12) | 알림이 터미널 화면 안에 모이지 않음 |
| `TODO.md` 보드 | 일반 Markdown 열람 | 칸반 시각화 |

어느 쪽이든 기능적으로 막히는 부분은 없고, Tern을 쓰면 편의성과 시각적 완성도가 올라갑니다.

**Tern 재평가 결과 (2026-11-06, M11 완료 후 M13 착수 전)**

사용자가 Stencil Tern 클로즈드 베타에 가입해 사용할 수 있습니다. 재평가 결과 다음과 같이 정합니다.

- **Intel 빌드**: 있습니다. 사용자가 베타 다운로드 화면에서 확인했습니다.
- **평가 범위**: Tern은 터미널·원격 접속 역할(세션 유지, 휴대폰 지시·승인, 관찰 화면)로만 평가합니다. 알림은 Tern이 맡지 않고 ntfy가 맡습니다(기술 설계 4.12).
- **M13**: tern 어댑터를 넣지 않습니다. tmux 어댑터만 만들고 어댑터 경계(`terminal_split`, `terminal_send`, `terminal_open_tab`)는 유지합니다.
- **채택**: 시범 평가 결과를 보고 사용자가 정합니다. 채택하면 tern 어댑터를 별도 작업으로 추가합니다.

공식 자료로 확인한 사실과 확인 필요 항목 (2026-11-06 기준)

| 항목 | 확인된 사실 | 확인 필요 |
| --- | --- | --- |
| 지원 플랫폼 | 플러그인 문서의 지원 표에 macOS, Linux, Windows, iOS, 웹 탭이 있음 | iOS 앱의 출시 여부와 배포 방식 |
| 원격 접속 | `tern remote serve`가 서버의 세션 데몬을 QUIC으로 제공하고, 주소나 tailnet 피어로 붙음 | 인증 방식, 포트 설정, 붙는 절차의 세부 |
| CLI 패널 제어 | 공식 소개 페이지에 `tern split`, `tern run`, `tern capture`, `tern events --filter`가 있음 | 패널에 입력 보내기, 새 탭 열기 |
| 재부팅 복원 | 재부팅하면 패널이 원래 디렉터리와 스크롤백으로 돌아옴 | launchd 연동 |
| 알림 | 플러그인 훅의 토스트는 앱 안에만 뜨고, 붙은 창이 없으면 버려짐 | 해당 없음 (평가 범위 밖) |
| 소스 | SDK(`stencil-hq/tern-sdk`)만 MIT | 앱 본체는 클로즈드 소스로 가정 |
| 자원 부담 | 공식 수치 없음 | Intel 맥에서의 메모리·CPU |

이름이 같은 다른 프로젝트(예: git 리뷰용 Tauri 앱 `Car-Role/tern`)의 배포 파일은 근거로 쓰지 않습니다.

비교 기준 (시범 평가, tmux 구성 대비)

- 재부팅 후 세션 복원과 launchd 연동
- Windows·모바일에서의 지시·승인 편의
- `tern` CLI로 관찰 패널과 D 레인 패널을 구현할 수 있는지
- Intel 맥에서의 메모리·CPU 부담
- 클로즈드 베타·클로즈드 소스 위험

운영 규칙

- 실행 호스트(Intel 맥)에는 다음 조건을 모두 갖췄을 때만 Tern을 설치합니다. 설치 시점은 사용자가 정합니다.
  - 사용자의 별도 승인
  - 실행 중인 작업 0건 (`orch status`로 확인)
  - 미리 정한 제거 절차: 데몬 종료, 로그인 항목 해제, 앱과 설정·데이터 디렉터리 삭제. 각 경로는 설치할 때 확인해 이 문서에 채웁니다.
- 설치 없이 써 보려면 Windows에서 Tern을 터미널로만 쓰고, 그 안에서 지금처럼 SSH로 맥의 tmux에 붙습니다. 이 방식은 Tern의 데몬 세션·원격 호스트 기능을 평가하지 않습니다.
- Tern 평가는 코드를 바꾸지 않으며 `orch` 작업을 만들지 않습니다.

## 5. 실행 흐름과 장애 처리

메인은 배분할 때마다 턴을 끝내고, 완료 알림이 올 때만 다시 깨어납니다.

**실행 흐름 예시**

1. 사용자 프롬프트 → 메인이 `explorer` 2건을 A 레인(백그라운드)으로 배분 → 턴 종료
2. `explorer` 완료 알림 → 메인이 확정 사실로 작업 3건을 분해하고 지시서 작성
3. `orch dispatch` ×3 → task-1·task-2는 B, task-3은 C로 `orch run`을 백그라운드 실행 → 배분 목록 보고 → 턴 종료
4. task-1 완료 알림 → 메인이 결과 JSON 확인 → `orch gate` → L3이므로 `reviewer`(A) 배분 → 턴 종료
5. `reviewer` 완료 알림 → P0/P1 없음 → `orch pr task-1` → 상태 보고 → `orch wait task-1 --merged`를 백그라운드 셸로 실행 → 턴 종료. 머지되면 완료 알림 → `orch close task-1` → `orch next`
6. task-2, task-3도 같은 흐름으로 처리. 대기 중이던 `queued` 작업은 완료 알림 시점에 이어서 배분

**장애 처리**

| 상황 | 감지 | 처리 |
| --- | --- | --- |
| 결과 JSON 누락·형식 오류 | `orch run` 검증 | `FAILED`(보고 누락), 1회 재시도 |
| 시간 초과 | `orch run 시간 상한` | `FAILED`(시간 초과), 워크트리 보존, 재분해 검토 |
| 한도 오류 | 유효한 결과가 없을 때 구조화된 오류, 이어서 로그 문구 감지 | `BLOCKED_QUOTA`, 워크트리·잠금 보존, 사용자 보고 |
| 메모리 정리로 강제 종료 | 종료 신호 | `FAILED`(강제 종료), 동시 실행 상한 하향 검토 |
| 메인 세션 종료 | SessionStart 훅 | `orphaned` 작업 목록 보고, 사용자 지시로 재개 또는 폐기 |
| 진행 방향 이탈 (관찰 중 발견) | 사용자 | `orch kill` → 지시서 수정 → 재배분 |
| 완료 알림의 종료 코드 오표시 | — | 영향 없음 (결과 JSON과 게이트로만 판정) |

**운영 주의**: 백그라운드 서브에이전트와 완료 알림 동작은 최근 버전에서 자주 바뀌고 있으므로, 안정적으로 동작하는 Claude Code 버전을 고정하고 업데이트는 확인 후 반영합니다.

## 6. 허브 운용, 테스트 모드, 환경 전제

허브가 유일한 진입점이고, 메인은 대상 위치에서 허브 설정을 주입받아 실행됩니다(H2). 상태는 모든 대상이 공유하는 SQLite 하나로 관리합니다.

**`orch open <대상>` 동작**

1. `targets.toml`에서 대상 경로를 확인하고, 대상 저장소의 원격 정보를 확인합니다. 사용자가 기본 작업 트리를 편집 중일 수 있으므로, 미커밋 변경이 있어도 경고만 합니다.
2. 터미널 어댑터로 tmux(또는 Tern) 세션을 열고, 그 안에서 메인 Claude Code를 **대상 저장소 위치에서** 실행합니다.
3. 실행 옵션으로 허브의 `config/settings.json`(훅, 접근 금지 규칙)을 주입하고, M16부터 `config/main.md`(메인 규칙), `config/agents/`(서브에이전트 정의)도 주입합니다. `~/.orch/<대상>`을 추가 디렉터리로 지정합니다(메인과 읽기 전용 서브에이전트가 워크트리와 리뷰 파일을 읽기 위함). 이 `--add-dir`은 메인에만 붙이며, Codex 서브에 `--add-dir`을 쓰지 않는 규칙(3장)과 별개입니다. 옵션 형식은 Claude Code 2.1.319에서 확인했습니다(기술 설계 5.2).
4. 관찰 패널(`orch watch`)을 함께 엽니다. 대상 저장소에는 어떤 파일도 쓰지 않습니다.

한 세션은 대상 하나만 다룹니다. 여러 대상을 동시에 열 수는 있지만, 동시 실행 상한과 잠금은 `state.db`에서 모든 세션이 공유합니다.

**대상 등록 정보 (`targets.toml`)**

```toml
[targets.sample-app]
path = "~/work/sample-app"                            # ~/ 기준만 저장 (공개 저장소에 커밋되므로 개인 경로 금지)
github = "owner/sample-app"
default_branch = "main"
setup_command = "npm ci"                              # 워크트리 생성 직후 샌드박스 밖에서 실행
test_command = "npm test"
lint_command = "npm run lint"
shared_paths = ["package-lock.json", "migrations/"]   # 메인 소유 공유 파일
safety_paths = ["scripts/**", "src/auth.py"]          # 안전 장치 경로, 생략하면 빈 목록 (v0.4.0부터)
```

`needs_review` 알림의 기준이 되는 안전 장치 경로는 대상별 `safety_paths`로 이 파일에 한 번만 둡니다. 형식은 `shared_paths`와 같습니다(기술 설계 4.12).

**상태 저장소**: 표준 라이브러리 `sqlite3`를 쓰고, 작업·잠금·실행 슬롯·실행 기록 테이블을 둡니다. 여러 `orch run`이 거의 동시에 끝나도 트랜잭션으로 안전하게 갱신됩니다. 작업별 등급, 모델, 강도, 소요 시간, 결과를 남겨 매핑표와 동시 실행 상한을 데이터로 조정하는 근거로 씁니다.

**테스트 모드** (`ORCH_FAKE_AGENTS=1`)

- `codex`와 `claude` 대신 `tests/fake_agents/`의 가짜 실행기를 호출해, 사용량을 쓰지 않고 레인·통지·게이트·장애 처리를 반복 검증합니다.
- `~/.orch`가 아닌 `ORCH_HOME`을 명시해야 켜집니다(기술 설계 5.1). 가짜 실행기는 `ORCH_HUB` 아래에서 찾습니다.
- 재현 시나리오: 성공, `PARTIAL`, 보고 누락, 시간 초과, 한도 오류 문구, 수정 범위 밖 변경, 테스트 파일 변경, 동시 완료.
- 1장 "시스템 완료 기준"의 장애 시나리오 검증은 이 모드로 수행합니다.

**정리 정책**

- PR이 머지되면 `orch close`가 워크트리를 제거하고 잠금을 해제합니다. 폐기된 작업의 워크트리는 즉시 제거합니다.
- 로그, 결과, 리뷰 파일은 작업이 `closed`·`discarded`가 된 뒤 30일 보존 후 `orch gc`로 정리하고, 이때 `git worktree prune`도 함께 실행합니다. 지시서와 `state.db`의 기록은 지우지 않으며, 작업이 없는 워크트리 디렉터리(하네스 PR용)는 보고만 합니다(기술 설계 4.10.1).

**환경 전제**

| 항목 | 기준 | 비고 |
| --- | --- | --- |
| 실행 호스트 | Intel 맥북 (macOS), 24시간 가동 | 맥 본체 설정은 아래 상시 운용 구성 참고 |
| Python | 3.14 이상 | 표준 라이브러리만 사용 |
| uv | 최신 | 허브 패키징, `uv tool install`로 전역 설치 |
| git | worktree 지원 버전 |  |
| Claude Code | 2.1.319로 고정 | Pro 로그인, Opus 5.5 지정 확인됨. 자동 업데이트를 끄고, `orch open`이 버전이 다르면 경고 (기술 설계 5.2) |
| Codex CLI | 0.159.1 이상에서 고정 | ChatGPT Plus 로그인, `gpt-6.1-sol` 호출 확인 필요 |
| gh CLI | 최신 | 개인 로그인 없음. GH\_TOKEN에 GitHub App 토큰을 넘겨 호출 |
| tmux | 유일한 터미널 백엔드 | Herdr는 보류, Tern은 터미널·원격 접속 역할로 시범 평가 중 |
| Tailscale | 맥, Windows, 휴대폰 | 원격 접속 경로 |
| ntfy | ntfy.sh 무료 플랜 | 사용자가 조치해야 할 때만 알림. 토픽은 `~/.orch/config`에만 두고, 본문은 대상·작업 id·이벤트 종류만 (기술 설계 4.12) |
| 휴대폰 SSH 앱 | Tailscale 경유 tmux 접속 | 지시와 승인 전용 |

**GitHub 인증 구성**

`orch`의 토큰 발급 기능이 완성되기 전까지는 아래 임시 스크립트를 씁니다. 맥 기본 내장 `openssl`, `curl`, `python3`만 사용합니다.

| 파일 | 역할 |
| --- | --- |
| `~/.orch/secrets/app.pem`, `app_id`, `installation_id` | GitHub App 개인 키와 ID (디렉터리 700, 키 600) |
| `~/.orch/bin/ghapp-token.sh` | JWT 서명 후 설치 토큰(1시간 유효)을 발급해 출력 |
| `~/.orch/bin/git-credential-ghapp.sh` | git 자격 증명 도우미. `get` 요청에 앱 토큰을 돌려줌 |

```ini
# ~/.gitconfig
[credential "https://github.com"]
	helper =
	helper = /Users/<사용자명>/.orch/bin/git-credential-ghapp.sh
[user]
	name = <앱 이름>[bot]
	email = <봇 사용자 ID>+<앱 이름>[bot]@users.noreply.github.com
```

- 빈 `helper =`는 기본 설정된 `osxkeychain` 도우미를 github.com에 대해 무효로 만듭니다.
- zsh에서 `!`가 들어간 값을 `git config`로 넣으면 히스토리 확장으로 값이 깨지므로, 도우미는 절대 경로로 등록합니다.
- `gh`는 `GH_TOKEN=$(~/.orch/bin/ghapp-token.sh) gh ...` 형태로만 호출합니다.

**셸 환경 (비대화형 실행)**

`ssh 호스트 '명령'`, 백그라운드 셸, launchd에서 실행되는 zsh는 로그인 셸이 아니어서 `~/.zshenv`만 읽습니다. 도구 경로는 반드시 `~/.zshenv`에 둡니다.

| 도구 | 설치 방식 | 경로 |
| --- | --- | --- |
| tmux | MacPorts | `/opt/local/bin/tmux` |
| Codex CLI | mise (전역 고정 `mise use -g codex@0.160.0`) | `~/.local/share/mise/shims/codex` |
| Claude Code | 공식 설치 | `~/.local/bin/claude` |

```bash
# ~/.zshenv
typeset -U path
path=(
  "$HOME/.local/bin"
  "$HOME/.local/share/mise/shims"
  /opt/local/bin /opt/local/sbin
  $path
)
export LANG=en_US.UTF-8
```

`orch`는 Claude Code와 Codex를 PATH 탐색이 아니라 `~/.orch/config`에 적은 **절대 경로**로 실행합니다. mise의 shims는 현재 디렉터리의 mise 설정에 따라 버전을 고르므로, 대상 저장소의 설정이 에이전트 CLI 버전을 바꾸지 않게 하기 위함입니다.

**상시 운용 구성 (launchd)**

`orch service install`이 사용자 영역(`~/Library/LaunchAgents/`)에 아래 세 에이전트를 설치합니다. 맥이 재부팅되고 자동 로그인되면 모두 다시 올라옵니다.

| 에이전트 | 실행 시점 | 동작 |
| --- | --- | --- |
| `orch.session` | 로그인 시 | `orch service restore`: 터미널 기록이 있는 대상 중 `orch-<대상>` 세션이 **없는** 대상만 `orch open --no-attach`로 엶. 세션이 있으면 메인이 죽어 있어도 새로 띄우지 않음 |
| `orch.doctor` | 10분마다 (`StartInterval`, 올릴 때 바로 실행하지 않음) | `orch doctor` 실행, 나빠진 항목만 알림. 메인 세션을 재기동하지 않음 |
| `orch.gc` | 매일 04:00 (`StartCalendarInterval`) | `orch gc` 실행 |

맥 본체 설정(정전 후 자동 부팅, 자동 로그인, 잠자기 비활성화, OS 자동 업데이트 해제, Tailscale 자동 시작)은 `orch`가 바꾸지 않고, 구축 체크리스트로 사용자가 직접 설정합니다.

**게이트 샌드박스 재측정 (macOS 업데이트 때)**

G2·G3의 `sandbox-exec` 프로필(기술 설계 4.5)은 측정한 macOS 버전에서만 검증된 것입니다. 사용자가 macOS를 업데이트하면 다음 배분 전에 아래 순서로 다시 측정합니다.

1. `orch status`에서 실행 중인 작업이 없는지 확인합니다.
2. `sw_vers`로 새 버전을 기록합니다.
3. 허브 저장소의 전체 테스트를 프로필 아래에서 실행해, 프로필 없이 실행했을 때와 통과 수가 같고 건너뜀이 0건인지 확인합니다.
4. 막아야 할 동작을 시험합니다: 외부 접속, `~/.orch/secrets`와 `~/.ssh` 읽기, 워크트리 밖 쓰기, 키체인 조회가 실패하고, `ps`, `git`, 임시 디렉터리 쓰기는 성공해야 합니다.
5. 결과와 버전을 이 문서의 측정 기록에 남기는 하네스 PR을 엽니다. 하나라도 어긋나면 게이트가 실패로 닫히므로, 프로필을 고치는 작업이 머지될 때까지 새 배분을 하지 않습니다.
