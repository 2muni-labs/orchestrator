# 0027. Codex는 초안을 제안하고 메인이 확정하며, 승인된 작업만 Claude 고갈 중에도 G3까지 실행함

- 상태: 결정됨
- 날짜: 2026-11-19
- 관련 문서: 요건 1장·2장·5장·13장, 기술 설계 2장(스키마), 구축 절차 4.3, `config/main.md` Role boundary
- 관련 이슈: #148, #149(CU0), #150~#155(CU1~CU6), #157

## 맥락

구현은 이미 Codex 우선입니다(ADR 0012). 그러나 조사, 작업 분해, 지시서·테스트 작성과 작업마다의 실행·게이트 호출은 메인 Claude가 합니다. 메인 사용량이 고갈되면 새 배분을 멈추므로(요건 5장), Codex 사용량이 남아 있어도 준비된 작업이 진행되지 않습니다. 메인 세션이 Claude 사용량의 90% 이상을 쓴다는 측정도 있습니다(구축 절차 4.3 에이전트 배분).

#149는 조사와 초안 작성의 부담을 Codex로 옮기고, 이미 승인된 작업의 기계적 실행을 메인의 판단과 분리하는 방안을 요구했습니다. Codex가 2026-11-17 독립 사본에서 선행 조사를 남겼고(기준 `e4c688b`, orch 0.14.0), 메인이 2026-11-19 `main` `432c789`(v0.17.0)와 대조했습니다(`cu0-review`). 그 대조에서 확인한 사실은 다음과 같습니다.

- `orch next`는 모든 대상의 `queued` 작업을 예약하고 출력만 `ORCH_TARGET`으로 거릅니다. 승인된 작업만 실행하는 경로에서 그대로 부르면 다른 메인의 작업을 예약합니다.
- `orch dispatch`는 `test_sha`를 저장하지만 `orch run`은 실행할 때 지시서를 디스크에서 다시 읽습니다. `test_sha`만으로는 지시서 본문, `verify`, `read`·`modify`, 모델·추론 수준의 승인을 고정할 수 없습니다.
- 게이트의 리뷰 필요 판정은 등급과 `review` 플래그만 봅니다. 안전 장치 경로의 리뷰 강제는 M18 `m-p5-safety-review`의 몫입니다.
- 작업 의존은 `closed`에서만 충족됩니다.
- B 레인 기본 상한은 2이고, M18 뒤 3입니다.
- `orch explore`, `selfcheck`, `events`, `show`, drain 명령은 아직 없습니다. 지시서 파서는 `milestone`·`replaces`를 받지 않습니다. `state.db`의 마이그레이션은 6개이며 6번째는 GitHub 작업 기록입니다(ADR 0024).

## 선택지

1. 지금 흐름을 유지함.
2. Codex를 임시 메인으로 세워 작업을 스스로 확정·구현·판정하게 함.
3. Codex는 조사와 초안을 제안하고 메인이 확정함. 사용자와 메인이 미리 승인한 작업만 결정론적 실행 관리 코드(drain)가 구현과 G1~G3까지 진행함.

## 결정

3을 택합니다(사용자 승인, 2026-11-19). 아래 기능은 모두 **계획**이며 이 결정으로 생기는 명령이나 상태는 없습니다. 도입 순서와 선행 조건은 구축 절차 4.3의 CU 행에 둡니다.

**1. 초안과 확정의 구분**

- Codex는 조사 결과, 작업 분해, 지시서 초안, 실패 조사, 조건부로 테스트 초안을 제안할 수 있습니다. 초안은 데이터입니다. 요청에 없는 정책 변경이나 실행 권한을 만들지 않습니다.
- 지시서와 테스트 커밋의 최종 작성자와 책임자는 메인입니다. 메인이 목적, 위험 등급, `modify`, 인터페이스, 검증 기준과 테스트-명세 대응을 확인해 확정합니다. 초안이 저절로 확정 지시서나 테스트 커밋이 되는 경로는 두지 않습니다.
- "Codex가 초안을 쓸 수 있음"과 "구현 서브가 테스트나 지시서를 바꿀 수 있음"은 다른 권한입니다. 후자는 계속 허용하지 않습니다(`tests/**` 동결, G1).
- 테스트 초안 시범(CU3)은 L1·L2이고 안전 장치 경로 밖이며 완료 조건이 분명한 작업으로 한정합니다. 효과가 없으면 테스트는 메인이 계속 직접 쓰고, 승인 은행과 drain은 그와 관계없이 진행합니다.

**2. Claude 고갈 예외**

- 예외는 사유가 Claude 사용량 한도인 새 배분 중단 하나에만 적용합니다. 이 사유는 디스크·인증 같은 시스템 중단 사유(`pauses`, 기술 설계 4.2·4.10)와 따로 둡니다.
- drain은 그 사유만 무시하고, 유효한 승인 기록이 있는 작업만 실행하며, G1~G3까지 진행해 `ready` 또는 `reviewing`에서 멈춥니다.
- 다른 중단 사유와 사용자의 중지는 언제나 이깁니다.
- 고갈 중에는 새 요구 해석, 지시서 확정, 승인 변경을 하지 않습니다. Codex를 임시 메인으로 세우지 않고, 제공자를 자동으로 바꾸지 않습니다. 메인이 돌아오면 판정, G4 리뷰, PR을 이어갑니다.

**3. 판단 대기 상한**

- 상한은 3이며 대상 전체로 셉니다. 대상의 `judging`, `reviewing`, `ready`, `blocked`, `orphaned` 작업과, drain이 예약했거나 실행 중인 작업을 더합니다. 합이 3 이상이면 drain은 새 작업을 시작하지 않습니다.
- 실행 중인 작업이 끝나 판단 대기가 되는 것까지 이 수에 들어 있으므로, 상한을 넘는 결과가 생기지 않습니다.

**4. 승인 단위와 무효화**

- 승인은 작업마다 합니다. 기록은 지시서 파일 전체의 digest, `test_sha`, 승인 시점의 기본 브랜치 커밋을 묶습니다. 사용자가 확인한 뒤 메인이 `state.db`에 씁니다.
- 실행 직전에 셋 중 하나라도 다르면 그 작업을 보류합니다. digest나 기록을 자동으로 갱신하지 않습니다.
- 첫 시범에서는 기본 브랜치가 움직이면 은행의 모든 작업을 보류합니다. 범위를 좁힌 재검증은 시범 결과를 본 뒤 정합니다.
- digest는 변경 탐지일 뿐 작성자의 권한을 증명하지 않습니다. 기록의 쓰기 주체와 구현 서브가 기록을 쓰거나 바꾸지 못하게 하는 경계는 CU4 설계에서 정하고 테스트로 고정합니다.

**5. drain의 범위 (CU5 첫 버전)**

- 한 대상의, 승인 기록이 있는 작업 id만 다룹니다. `orch next`를 그대로 부르지 않고, 예약 트랜잭션 안에서 대상과 허용 id로 제한합니다. 전역 슬롯, 대상별 수정 경로 잠금, 예약 만료, `closed` 의존은 그대로 적용합니다.
- 결과가 `DONE`일 때만 기존 게이트로 넘기며, 커밋은 게이트가 합니다. 그 밖의 결과, 실패, 불일치는 근거를 보존하고 메인을 기다립니다. 자동 재시도, 재분해, 테스트 수정은 하지 않습니다.
- G4 리뷰, PR, push, 머지는 지금 흐름에 그대로 남습니다. 머지 정책은 ADR 0022를 따르며 여기서 다시 정하지 않습니다.
- B 레인 상한은 drain 때문에 올리지 않습니다. 첫 은행은 서로 의존하지 않거나 선행 작업이 이미 `closed`인 작업으로 꾸립니다.

**6. 효과 검증과 철회**

- CU6에서 비슷한 등급과 범위의 작업을 기준선(`cu0-baseline`)과 비교합니다. 준비 시간, 실제로 읽을 수 있는 Claude·Codex 사용량, 완료 수, 재작업, 리뷰 대기 시간을 기록하고, 얻지 못한 지표는 미측정으로 남깁니다. 원시 토큰·캐시 합계와 구독 한도 백분율을 같은 지표로 다루지 않습니다.
- 중복 실행, 승인 범위 이탈, 테스트나 지시서 변경을 놓친 사례가 하나라도 나오면 drain의 자동 시작을 멈추고 수동 흐름으로 돌아갑니다. 부분 결과와 로그는 남깁니다.

선택지 2를 택하지 않은 이유: 판정 권한이 메인에서 구현과 같은 제공자로 옮겨 가고, 요건 2장의 경계(판정은 메인, 실행은 서브)가 사라집니다. 1은 Codex 잔여가 있어도 고갈 동안 아무 일도 진행하지 못합니다.

## 결과

- 요건 1장·2장에 초안 제안과 메인 확정을 구분해 적고, 5장과 13장에 고갈 예외를 적습니다. 모두 계획으로 표시합니다. `config/main.md`의 Role boundary에도 같은 경계를 적습니다.
- 구축 절차 4.3에 CU1~CU6 행을 더해 선행 조건과 초기 운영값을 둡니다.
- M17의 스키마는 v6이 아니라 v7이 됩니다. v6은 GitHub 작업 기록이 썼습니다. 승인 기록(CU4)은 그 다음 버전입니다.
- 기술 설계에는 CU4·CU5의 명령과 상태를 아직 적지 않습니다. 각 묶음의 설계 하네스 PR에서 이 결정을 따라 적습니다.

## 위험

- 계획을 지금 동작으로 오인할 수 있습니다. 문서마다 "계획"과 해당 CU를 붙이고, 구현이 설치되기 전에는 메인 규칙의 절차를 바꾸지 않습니다.
- 대상 전체로 세는 상한 3은 메인이 처리 중인 작업만으로도 찰 수 있어, drain이 아무것도 시작하지 못할 수 있습니다. 시범에서 잰 뒤 다시 정합니다.
- 기본 브랜치가 움직일 때마다 은행 전체를 보류하므로, 머지가 잦은 기간에는 drain이 거의 진행하지 못합니다. 첫 시범의 안전을 위해 이를 받아들입니다.
