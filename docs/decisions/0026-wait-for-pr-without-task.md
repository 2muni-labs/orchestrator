# 0026. 작업 없는 PR도 orch wait가 기다리고 메인은 GitHub를 직접 폴링하지 않음

- 상태: 결정됨
- 날짜: 2026-11-19
- 관련 문서: 기술 설계 4.7.2, 실행 설계 3장, `config/main.md` Merge policy·GitHub authentication

## 맥락

`orch wait <id> --merged`(ADR 0020)는 작업이 있는 PR만 기다립니다. 작업이 없는 하네스 PR은 메인이 필수 체크 통과를 직접 확인하고 `verify-deep`을 붙여야 했습니다. 메인은 이를 셸 루프로 기다렸습니다.

2026-11-19 하네스 PR #520에서 이 루프가 git 저장소가 아닌 디렉터리에서 실행됐습니다. `gh`는 저장소를 정하지 못해 매번 실패했고, 루프는 표준 오류를 버리고 실패를 "아직 끝나지 않음"으로 읽었습니다. 그래서 `ci`가 통과한 뒤 35분 동안 라벨이 붙지 않았고, 사용자가 발견했습니다. 임시 루프는 저장소 지정, 오류 처리, 연속 실패 한도, 대기 상한을 매번 새로 써야 하며, 이번처럼 그중 하나가 빠지면 조용히 멈춥니다.

## 선택지

1. 메인 규칙에 루프 작성 요령만 더함. 메인이 루프를 계속 씀.
2. `orch wait`에 PR 번호나 URL로 기다리는 형태를 더하고, 메인은 GitHub 상태를 직접 폴링하지 않음.
3. 하네스 PR도 `orch` 작업으로 만듦.

## 결정

2를 택합니다(사용자 승인, 2026-11-19).

- `orch wait --pr <번호|URL> --merged`를 더합니다. 작업 id 대신 PR을 받으며, 대상은 세션의 `ORCH_TARGET`입니다. 확인 순서, 종료 코드, 연속 실패 한도(10회), 대기 상한은 작업 PR과 같습니다(기술 설계 4.7.2).
- 리뷰 라벨은 언제나 `verify-deep`입니다. 작업이 없으므로 등급이 없고, 머지 정책이 작업 없는 PR을 깊은 리뷰로 정하기 때문입니다.
- 세션 대상 저장소 밖의 PR, 작업에 묶인 PR은 거부합니다. 작업 PR은 상태 확인이 있는 `orch wait <id>`로 기다립니다.
- 메인은 GitHub 상태를 기다리는 셸 루프를 쓰지 않고 `orch wait`를 씁니다. `--pr`이 설치되기 전의 하네스 PR처럼 `orch wait`가 아직 맡지 않는 경우에만 루프를 쓰며, 그 루프는 모든 `gh` 호출에 `-R`을 주고, 표준 오류를 버리지 않고, 첫 실패에서 끝나고, 시간 상한을 둡니다. 일회성 `gh` 호출도 `-R`을 주고 표준 오류를 버리지 않습니다.

3을 택하지 않은 이유: 하네스 PR은 공유 경로를 바꾸므로 `orch prepare`가 거부하며(기술 설계 2장 지시서 규격), 지시서·게이트·리뷰 없이 메인이 직접 쓰는 PR이라는 정의를 바꿔야 합니다. 1은 같은 실수가 다시 날 수 있는 구조를 남깁니다.

## 결과

- 구현은 후속 작업 `m-wait-pr`(`waiter.py`, `cli.py`)이 맡습니다. `github.py`는 안전 장치 경로이므로 바꾸지 않고 기존 조회와 라벨 함수를 씁니다.
- 허브 `CLAUDE.md`의 하네스 PR 절차("`orch wait`는 해당하지 않음", "라벨을 직접 붙임")는 그 버전(v0.18.0)을 설치한 뒤 버전 PR `h-version-0180`에서 `orch wait --pr`로 바꿉니다. 그 전까지는 위의 루프 규칙을 따릅니다.
- `orch wait --pr`은 작업에 묶인 PR인지 확인할 때만 `state.db`를 읽고 쓰지는 않으므로, 하네스 PR의 상태는 지금처럼 GitHub 작업 기록의 `pr_url`로만 추적됩니다(ADR 0024).

## 위험

- 하네스 PR은 `orch close`가 없으므로, 머지 뒤 워크트리와 로컬 브랜치 정리는 메인이 계속 직접 합니다.
- 알림의 중복 억제 키에서 작업 id 자리에 `pr-<번호>`를 씁니다. 같은 번호의 작업 id가 생기면 키가 겹칠 수 있으나, 작업 id 형식에서 `pr-` 접두사를 쓰지 않으면 피할 수 있으며 피해는 알림 1건의 억제에 그칩니다.
