# 0025. 작업 우선도는 메인이 정하고 계획 파일은 orch가 state.db에서 만듦

- 상태: 결정됨
- 날짜: 2026-11-19
- 관련 문서: 기술 설계 4.11, 실행 설계 2장, `config/main.md`, `templates/task.md`

## 맥락

작업의 우선도와 의존관계를 기록하는 절차가 없어서, 세션이 바뀔 때마다 메인이 남은 작업과 선행 조건을 다시 파악해야 했습니다. 제안 Discussion #510과 PR #512는 두 가지를 담았습니다. 하나는 `orch next`가 우선도로 대기열을 정렬하는 자동 정렬이고, 다른 하나는 메인이 계획 파일, 지시서 본문, 이슈의 Planning 블록, Projects의 Priority 필드를 손으로 갱신하는 절차입니다. 손 갱신 절차는 0024가 피하려 한 문제를 다시 만듭니다. 갱신할 곳이 많아 메인 세션의 시간과 컨텍스트를 쓰고, 기록끼리 어긋날 수 있습니다.

## 선택지

1. #512대로 메인이 계획 파일과 GitHub 필드를 손으로 갱신하고, 이어서 자동 정렬을 구현함.
2. 우선도와 외부 의존은 메인이 지시서 본문에 한 번만 쓰고, 계획 파일은 `orch`가 `state.db`와 지시서에서 만듦. 자동 정렬은 하지 않음.
3. 계획을 기록하지 않음.

## 결정

2를 택합니다(사용자 결정, 2026-11-18).

- 자동 정렬은 하지 않습니다. `orch next`는 지금처럼 오래된 작업부터 봅니다.
- 작업 우선도(P0–P3)는 위험 등급, 리뷰 심각도와 별개입니다. 메인이 계획 승인 때 정하고, 지시서 본문의 고정된 줄에 한 번 씁니다. TOML 필드는 늘리지 않습니다.
- 실행할 작업 사이의 의존은 `depends_on`에만 둡니다. 설치, 측정, 결정, 수락 같은 외부 의존은 근거와 함께 지시서 본문에 씁니다.
- `orch`는 TODO.md와 같은 시점에 프로젝트 그룹마다 `~/.orch/<대상>/plans/<그룹>.md`를 만듭니다(기술 설계 4.11). 에이전트 토큰을 쓰지 않으며, 메인은 이 파일을 읽기만 합니다.
- GitHub에는 우선도를 쓰지 않습니다. Planning 블록, Priority 필드, 동기화 대기 기록도 두지 않습니다. 계획은 로컬에만 둡니다.
- 머지는 설치나 실제 사용의 수락을 대신하지 않습니다.

1을 택하지 않은 이유는 맥락에 적은 손 갱신의 비용과 어긋남입니다. 자동 정렬은 실행 중인 작업과 잠금의 상호작용을 바꾸는 반면, 지금의 동시 실행 한도(1–2개)에서는 얻는 것이 적습니다.

## 결과

- 이 PR은 규칙과 설계만 바꿉니다. 계획 파일 생성은 후속 작업 `m-plan-render`가 구현하고, 메인 규칙의 "계획 파일을 먼저 읽음"은 그 버전이 설치된 뒤 추가합니다.
- #512의 영문 문서와 별도의 한국어 참조 문서는 만들지 않습니다. 설계 문서가 원본이고, 저장소 소개는 한국어 `README.md`로 합니다.
- 우선도는 계획 파일에서 보이지만 배분 순서를 바꾸지 않습니다. 순서를 바꾸려면 메인이 배분 시점을 고릅니다.

## 위험

- 지시서 본문의 우선도 줄 형식이 틀리면 계획 파일에 `-`로 나옵니다. 판정이나 배분에는 쓰지 않으므로 피해는 표시에 그칩니다.
- 계획 파일은 마지막 갱신 시점의 내용이므로 잠시 뒤처질 수 있습니다. 상태의 원본은 언제나 `state.db`입니다.
