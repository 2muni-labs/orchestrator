# 0020. 라벨로 시작하는 예약 작업이 리뷰하고 머지함

- 상태: 결정됨, 일부 대체됨 (0022)
- 날짜: 2026-11-16
- 관련 문서: 요건 정의 9장, 기술 설계 4.7·4.7.2·4.12, 실행 설계 3장, 보안 설계 11장, `config/main.md` Merge policy

## 맥락

PR의 검증과 머지는 사용자가 claude.ai 채팅의 검증 세션에 병합 표를 넘기며 직접 지시했습니다. PR마다 사용자가 개입해야 했고, 메인 세션은 그동안 대기했습니다. 합친 상태의 전체 테스트는 메인과 검증 세션이 각자 손으로 돌렸습니다.

측정(2026-11-16, 봇 토큰):

- 봇이 붙이고 뗀 라벨은 PR 타임라인에 `LabeledEvent`·`UnlabeledEvent`로 남고, 행위자(`2muni-labs-agent`, Bot)와 시각이 기록됩니다.
- 커밋의 check-runs, check-suites, status, 저장소의 Actions 워크플로, 기본 브랜치 규칙은 모두 조회됩니다(HTTP 200). 저장소가 공개라서 이 결과는 앱 권한을 증명하지 않습니다. 비공개 대상에는 Checks 읽기, Commit statuses 읽기, Actions 읽기 권한이 필요합니다.

## 선택지

1. 지금처럼 사용자가 검증 세션에 직접 지시합니다.
2. 봇이 필수 체크 통과 뒤 스스로 머지합니다. 봇은 자기 PR을 승인할 수 없고, 에이전트가 머지하지 않는다는 원칙을 깹니다.
3. 봇은 라벨만 붙이고, 사용자 계정의 클라우드 예약 작업이 라벨 이벤트로 시작해 리뷰하고 머지합니다.

## 결정

3을 택합니다.

- 라벨은 `verify-light`, `verify-deep`, `needs-user`, `user-approved`, `changes-requested`, `review-overridden` 여섯 개입니다.
- 등급 L1·L2이면서 변경 파일이 안전 장치 경로 밖이면 `verify-light`, 그 밖에는 `verify-deep`입니다. `verify-light`는 예약 작업이 혼자 승인하고 머지합니다. `verify-deep`은 리뷰 뒤 사용자가 `user-approved`를 붙여야 머지합니다. `review-overridden`은 지금처럼 사용자가 직접 머지합니다.
- GitHub Actions 워크플로가 PR의 합친 상태에서 전체 테스트와 ruff를 실행하고, 사용자가 이를 main 규칙 세트의 필수 체크로 둡니다. 리뷰 라벨은 필수 체크가 통과한 뒤에만 붙습니다.
- 라벨을 붙이는 일과 대기는 `orch wait`가 GitHub 조회만으로 처리하며 모델을 부르지 않습니다. 횟수 제한(수정 1회, 다시 붙이기 1회)은 타임라인의 라벨 이벤트로 세므로 `orch wait`를 다시 실행해도 결과가 같고, `state.db`에 새 열이 필요 없습니다.
- 필수 체크 이름은 규칙 세트에서 읽습니다. 목록을 다른 곳에 복제하지 않습니다.
- 봇은 `user-approved`를 붙이거나 떼지 않습니다. `github.py`가 거부하고 테스트로 고정합니다.
- 정책의 원본은 `config/main.md`의 Merge policy 절 하나이며, 예약 작업은 이를 PR 브랜치가 아닌 `origin/main`에서 읽습니다.

## 결과

- 사용자의 개입은 `verify-deep` PR의 `user-approved`, `review-overridden` PR의 머지, `needs-user`와 두 번째 `changes-requested`에 대한 판단으로 줄어듭니다.
- 메인 세션은 PR마다 대기하지 않고, 작업 묶음이 끝나면 `/clear`로 비웁니다.
- 새 위험: 봇 키가 유출되면 공격자가 PR을 올리고 `verify-light`를 붙여 예약 작업의 머지를 유도할 수 있습니다. 예전에는 사용자의 명시적 지시가 있어야 했습니다. 방어선은 필수 체크, 예약 작업의 자체 리뷰, 예약 작업이 `origin/main`의 안전 장치 경로로 `verify-light` 자격을 다시 판정하는 것, `user-approved`의 행위자가 사용자인지 확인하는 것입니다. 등급은 봇이 쓴 리뷰 패킷에서 오므로 등급만으로는 방어선이 되지 않습니다(보안 설계 11장).
- 워크플로 파일은 안전 장치 경로(`.github/workflows/**`)에 들어갑니다. 봇 App에는 `workflows` 권한이 없어 워크플로 파일이 든 push가 거부됩니다(2026-11-16 측정). 이 권한은 주지 않습니다. 필수 체크를 봇이 바꿀 수 없어야 하기 때문입니다. 워크플로 파일은 사용자가 자기 계정으로 추가하고 고칩니다.
- `orch wait`의 기본 대기 상한은 90분에서 12시간으로 늘어납니다.
