# 0024. GitHub 이슈와 Projects는 메인이 기존 작업 기록에 연동함

- 상태: 결정됨 (이 PR 머지 후 적용)
- 날짜: 2026-11-17
- 관련 문서: 요건 3장·10장, 기술 설계 4.17, 실행 설계 2장, 보안 설계 12장, `config/main.md`

## 맥락

작업 이력을 8개 프로젝트와 336개 이슈로 정리했으나 메인 절차에 연동 규칙이 없으면 이후 상태가 어긋납니다. 사용자는 범위를 정책·메인 작업 절차 연동으로 확정했습니다. CLI 자동 동기화는 요청 범위에 넣지 않습니다. 번호 0023은 열린 PR #145의 제안에 쓰여 중복을 피하려고 0024를 사용합니다.

## 선택지

1. 기존 기록을 GitHub로 옮겨 상태 원본을 교체함.
2. 기존 기록을 유지하고 메인이 작업 단계마다 이슈·프로젝트를 갱신함.
3. DB·CLI에 outbox와 자동 동기화를 구현함.

## 결정

2를 택합니다. 로컬 상태·결과·리뷰·git으로 판정하고 GitHub는 그 요약을 보여 줍니다. 식별과 재시작을 위한 대응표와 확인되지 않은 갱신을 대상 런타임에 영속화하고, 검토된 저장소 seed로 기존 연결을 복구합니다. 서브는 결과만 보고하며 메인이 봇 인증으로 외부 기록을 갱신합니다.

갱신은 계획 승인, 배분, 막힘·사용자 대기, PR 생성, 완료, 폐기의 여섯 시점으로 제한합니다. 실행·게이트·리뷰 통지마다 갱신하면 작업 하나에 열 번 가까이 API 호출과 재조회가 생겨 메인 세션의 시간과 컨텍스트를 많이 쓰기 때문입니다. 갱신은 메인 한 곳이 하므로 잠금 파일과 revision 같은 코드 수준의 장치를 메인의 수작업 절차에 두지 않습니다.

3은 지금 하지 않습니다. 메인 절차로 운용해 보고, 갱신 누락이나 메인 세션의 부담이 반복되면 같은 규칙을 `orch` 명령(대응표 읽기·쓰기, 재조회, 확인되지 않은 갱신의 재전송)으로 옮기는 후속 작업을 계획합니다.

생성 응답만으로 프로젝트 소속을 믿지 않고 다시 조회합니다. 실제 마이그레이션에서 생성 인자가 반영되지 않았고, 이슈 close 자동화가 Cancelled를 Done으로 덮었습니다. 명시적 소속 추가와 종료 후 상태 재대조를 절차에 넣습니다. 보고 DONE·게이트 통과·PR 생성은 완료 이슈 종료의 근거가 아닙니다.

## 결과

- CLI·스키마·훅·서비스를 바꾸지 않고, 머지된 규칙을 새 orch open이 주입하면 적용됩니다.
- 메인이 꺼져 있는 동안에는 즉시 동기화되지 않습니다. 다음 턴·세션에서 pending과 현재 근거를 재대조합니다.
- API 실패로 기존 task/gate 결과를 되돌리지 않습니다. 인증 장애·훅 차단의 기존 중단 규칙은 유지합니다.
- 단일 task·집계·하네스·측정의 완료 책임을 구별해 상위 이슈를 일찍 닫지 않습니다.
- 원문 로그·인증·개인 경로는 공개 이슈에 올리지 않으며, Projects 접근을 위해 개인 인증이나 머지 권한을 추가하지 않습니다.

## 위험

- App에 Issues 쓰기와 조직 Projects 쓰기가 더해집니다. 봇 키가 유출되면 공격자가 이슈를 고치거나 닫고 조직의 프로젝트 항목과 Status를 바꿀 수 있습니다.
- 작업의 실행·판정·머지는 GitHub 기록을 근거로 쓰지 않으므로 피해는 기록의 표시에 그칩니다. 메인은 로컬 근거로 다시 계산해 바로잡습니다.
- 메인이 갱신을 빠뜨리면 기록이 어긋납니다. 세션 시작과 묶음 종료의 재전송으로 줄이지만, 메인이 꺼져 있는 동안의 즉시 반영은 보장하지 않습니다.
