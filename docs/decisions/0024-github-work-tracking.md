# 0024. GitHub 이슈와 Projects는 orch가 작업 기록에서 동기화함

- 상태: 결정됨 (이 PR 머지 후 적용)
- 날짜: 2026-11-17
- 관련 문서: 요건 3장·10장, 기술 설계 4.17, 실행 설계 2장, 보안 설계 12장, `config/main.md`

## 맥락

작업 이력을 8개 프로젝트와 336개 이슈로 정리했으나 메인 절차에 연동 규칙이 없으면 이후 상태가 어긋납니다. 처음 제안(#487)은 메인이 작업 단계마다 이슈와 프로젝트를 손으로 갱신하는 절차였습니다. 검토에서 두 문제가 나왔습니다. 잠금·revision·재조회 같은 코드 수준의 일을 메인이 수작업으로 해야 하고, 작업 하나에 갱신이 열 번 가까이 생겨 메인 세션의 시간과 컨텍스트를 많이 씁니다. 번호 0023은 열린 PR #145의 제안에 쓰여 중복을 피하려고 0024를 사용합니다.

## 선택지

1. 기존 기록을 GitHub로 옮겨 상태 원본을 교체함.
2. 기존 기록을 유지하고 메인이 작업 단계마다 이슈·프로젝트를 갱신함.
3. `orch` 명령이 `state.db`에서 이슈와 프로젝트를 주기적으로 동기화함.

## 결정

3을 택합니다. 상태의 원본은 계속 로컬 상태·결과·리뷰·git이고, GitHub는 그 요약을 보여 줍니다. 반영은 메인이 아니라 `orch track sync`가 합니다. launchd가 주기적으로 실행하며, 실행마다 기록별로 원하는 상태를 근거에서 계산해 실제와 다른 것만 고치고 다시 읽어 확인합니다(기술 설계 4.17). 반영 지연은 실행 간격까지 허용합니다(사용자 결정).

2를 택하지 않은 이유는 맥락의 두 문제입니다. 3에서는 잠금, 재시도, 재조회, close 자동화가 덮은 `Cancelled`의 재적용이 테스트된 코드가 되고, 메인은 계획 승인 때 기록과 이슈를 연결하는 일만 합니다. 원하는 상태를 매번 다시 계산하므로 놓친 이벤트나 실패도 다음 실행이 바로잡습니다.

생성 응답만으로 프로젝트 소속을 믿지 않고 다시 조회합니다. 실제 마이그레이션에서 생성 인자가 반영되지 않았고, 이슈 close 자동화가 Cancelled를 Done으로 덮었습니다. 보고 DONE·게이트 통과·PR 생성은 완료 이슈 종료의 근거가 아닙니다.

`orch track sync`가 설치되기 전에는 메인이 계획 승인 때 대응만 기록하고 상태는 갱신하지 않습니다. 그 사이 어긋난 기록은 첫 동기화가 바로잡으므로, 그동안의 수작업 갱신은 하지 않습니다.

## 결과

- 이 정책 PR은 규칙과 설계만 바꿉니다. 동기화는 후속 묶음(측정, 대응표의 DB 이관, Projects API 모듈, 동기화 엔진과 CLI, launchd 연결과 doctor 점검)으로 구현합니다.
- 구현 전까지 이슈와 프로젝트의 상태는 실제 진행보다 늦습니다.
- API 실패로 task/gate 결과를 되돌리지 않습니다. 인증 장애·훅 차단의 기존 중단 규칙은 유지합니다.
- 단일 task·집계·하네스·측정의 완료 책임을 구별해 상위 이슈를 일찍 닫지 않습니다.
- 원문 로그·인증·개인 경로는 공개 이슈에 올리지 않으며, Projects 접근을 위해 개인 인증이나 머지 권한을 추가하지 않습니다.

## 위험

- App에 Issues 쓰기와 조직 Projects 쓰기가 더해집니다. 봇 키가 유출되면 공격자가 이슈를 고치거나 닫고 조직의 프로젝트 항목과 Status를 바꿀 수 있습니다.
- 작업의 실행·판정·머지는 GitHub 기록을 근거로 쓰지 않으므로 피해는 기록의 표시에 그칩니다. 다음 동기화가 로컬 근거로 다시 계산해 바로잡습니다.
- 봇 토큰으로 GitHub에 쓰는 무인 작업이 하나 늘어납니다. 쓰기 범위(대상 저장소의 이슈, 등록된 프로젝트)와 본문 형식을 코드로 고정하고 `redact`를 거칩니다.
- 다른 세션(예: Codex)이 같은 이슈를 손으로 바꾸면 다음 동기화가 근거대로 되돌립니다. 이슈의 사용자 본문은 건드리지 않습니다.
