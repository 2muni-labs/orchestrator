# 0018. Codex 네트워크는 orch의 허용 목록 프록시로

- 상태: 결정됨
- 날짜: 2026-11-15
- 관련 문서: `보안 설계.md` 5장, 기술 설계 4.6, ADR 0016

## 맥락

ADR 0016으로 Codex는 자체 샌드박스를 끄고 orch 프로필 안에서 실행합니다. 그런데 Codex 자체 샌드박스의 `workspace-write`는 Codex가 실행하는 명령의 네트워크를 막았습니다. 이를 끄면, Codex의 API 접속을 위해 프로필이 열어 둔 네트워크를 그 명령들도 같이 씁니다. 또 S-M3에서 바인드 주소 필터는 포트만 제한했습니다.

측정(S-M2b, codex-cli 0.160.0, macOS 15.8.1)의 결과는 다음과 같습니다.
- Codex는 `HTTPS_PROXY`를 따랐고, 모든 연결이 프록시의 CONNECT로 `chatgpt.com`과 `ab.chatgpt.com`의 443에 갔습니다. 웹소켓이나 직접 연결은 없었습니다.
- 프로필이 `localhost:<포트>`로 나가는 연결만 허용해도 Codex는 정상으로 답했습니다. 프록시 환경 변수가 없으면 `turn.failed`, 종료 코드 1로 실패했습니다.
- Codex가 실행한 명령의 결과: 허용 목록 밖 호스트는 프록시가 403으로 거부했고, 직접 연결과 DNS 조회는 프로필이 거부했습니다.
- 나가는 연결의 `localhost:<포트>` 필터는 주소도 루프백으로 제한했습니다. 같은 필터에서 `1.1.1.1:443`은 거부됐습니다.

## 선택지

1. orch가 실행마다 샌드박스 밖에 허용 목록 프록시를 띄우고, 프로필은 `localhost:<포트>`로 나가는 연결만 허용함
2. 프로필에서 네트워크를 열어 둠(명령도 인터넷 접속 가능)
3. B 레인 구현은 지금처럼 Codex `workspace-write`로 두고, 리뷰와 탐색만 orch 프로필로(ADR 0016의 선택지 2)

## 결정

1을 택하고, ADR 0016을 리뷰, `orch explore`, B 레인 구현 모두에 그대로 적용합니다. 2는 명령의 네트워크를 막던 지금보다 약해집니다. 3은 구현 서브가 `~/.orch`를 읽을 수 있는 위험을 남깁니다. 1은 그 위험을 없애면서 명령의 외부 접속도 막습니다.

## 결과

- 프록시는 표준 라이브러리로 만듭니다. CONNECT만 받고 허용 목록의 호스트와 443만 통과시키며, 요청마다 호스트·포트·판정을 실행 로그에 남깁니다. 실행이 끝나면 함께 끝냅니다. 포트는 실행마다 고릅니다.
- 허용 목록은 측정에서 쓰인 호스트로 둡니다(`chatgpt.com`, `ab.chatgpt.com`). 토큰 갱신 등 다른 호스트가 필요한지는 `m-p5-codex-sandbox` 지시서를 쓰기 전에 확인합니다. 허용 목록 밖으로 나가려다 거부된 연결은 실행 결과에 드러나게 합니다.
- 남은 통로: Codex가 실행한 명령도 허용 목록의 호스트에 접속할 수 있고, Codex가 읽어야 하는 `~/.codex`의 인증 파일을 읽을 수 있습니다. 같은 프로세스 트리 안이라 프로필로는 둘을 나눌 수 없습니다. 제3자에게 데이터를 보내려면 ChatGPT 백엔드를 거쳐야 하는 경로로 좁혀집니다.
- Codex나 macOS 버전을 올릴 때 S-M2b를 다시 측정합니다(`config/pins.toml`).
