# 0030. 입력 대기는 events 테이블에 함께 기록하고 표시 파일로 열린 대기를 가림

- 상태: 결정됨
- 날짜: 2026-11-24
- 관련 문서: 기술 설계 2장(스키마 v9), 4.13 "입력 대기 기록", 요건 OR-2

## 맥락

작업공간(요건 OR-2)은 메인 세션이 사람의 입력을 기다리는 시간을 보여야 합니다. 설계는 대기의
시작과 끝을 기록해 `orch events`로 내도록 했지만(P5-M4 측정), 저장 위치와 노출 형식은 정하지
않았습니다. `orch events`는 작업 상태 전이만 내고, 조회는 `tasks`와 내부 조인하며, 읽는 쪽은
마지막으로 받은 `id` 하나로 이어 받습니다. 대기는 작업이 아니라 세션의 사건입니다. 또 끝을
알리는 훅 가운데 `PostToolUse`는 도구 호출마다 오므로, 훅마다 `state.db`를 열면 메인 세션이
느려지고 잠금 경합이 생깁니다.

## 선택지

저장:

1. `events`에 `kind`, `session_id`, `target` 열을 더하고 대기 행은 `task_id`를 NULL로 둠
2. 새 테이블 `input_waits`를 두고 `orch events`가 두 테이블을 합쳐 냄
3. 새 테이블과 새 명령(`orch waits`)

열린 대기 판정:

1. 런타임 디렉터리의 세션별 표시 파일
2. 끝 훅마다 `state.db`에서 그 세션의 마지막 대기 행을 조회

## 결정

저장은 1을 택합니다. `events.task_id`는 NULL을 허용하고 외래 키가 없어 열 추가만으로 되며(추가형
변경, 스키마 v9), `id` 하나의 커서로 전이와 대기를 함께 이어 받을 수 있습니다. 2는 두 테이블의
`id`가 따로 늘어 커서가 둘이 되고, 3은 작업공간이 두 흐름을 따로 따라가야 합니다. `task_id`와
상태가 NULL일 수 있어 출력 형식이 바뀌므로 `orch events`는 v2로 올립니다.

열린 대기는 1을 택합니다. 끝 훅 대부분은 파일 하나의 존재만 확인하고 `state.db`를 열지 않습니다.
시작은 `O_EXCL` 생성으로, 끝은 지우기 성공으로 한 번만 기록되므로 겹친 시작과 경합하는 끝 훅이
기록을 둘로 만들지 않습니다.

## 결과

- 상태 전이를 쓰는 코드와 기존 행은 바뀌지 않습니다. `kind`가 NULL인 행은 전이로 읽습니다.
- 세션이 `SessionEnd` 없이 죽으면 끝이 없는 시작이 남습니다. 읽는 쪽은 "끝 모름"으로 다루고,
  `SessionStart` 훅이 7일 지난 표시 파일을 지웁니다.
- Esc 거부는 다음 입력 뒤에야 끝이 기록되므로 대기가 실제보다 길 수 있습니다(P5-M4).
- 새 훅 등록은 설치 뒤의 하네스 PR이며, 그때 도구 호출마다 프로세스가 하나 더 뜨는 지연을 잽니다.
- 스키마 v9를 이 기능이 쓰므로 CU4의 작업별 승인 기록(ADR 0027)은 v10입니다.
