# orch 작업공간(deck) 기획 초안

> **초안입니다.** 이 문서는 논의 중인 내용이며 설계의 근거가 아닙니다. 확정된 부분은 `docs/design/`으로
> 옮기고, 이 파일은 지우거나 결정 기록으로 줄입니다. 구성 요소 이름 `deck`(명령 `orch deck`)은 가칭입니다.

- 작성: 2026-11-15, Phase 4 완료(PR #134) 직후
- 방침(2026-11-15, 사용자 결정): **orch를 확장해 작업공간(화면 출력부)까지 이 저장소 하나가 맡습니다.** 별도 저장소와 서브모듈은 쓰지 않습니다.
- 배경: Tern(Stencil, 클로즈드 베타)의 기능 일부와 Hyprland의 조작감을 가져와, orch와 외부 에이전트를 한 화면에서 조작하고 관찰하는 작업공간을 만듭니다.

## 0. orch의 정의

> **orch는 메인 Claude Code가 내린 판단을 기계적으로 집행하고, 검증하고, 기록하는 "테스트 우선·게이트 기반 코드 변경 파이프라인"입니다. 여기에 그 파이프라인을 24시간 돌리는 운용 관리가 더해집니다.**

이 방침에 따라 orch는 세 구성 요소를 갖습니다.

| 구성 요소 | 역할 | 지금 |
| --- | --- | --- |
| 파이프라인 | 위 정의. 대상, 작업, 레인, 게이트, PR | 있음 (`src/orch`) |
| 운용 관리 | doctor, pause, gc, launchd, 세션 복원, 알림 | 있음 |
| 작업공간(deck) | 에이전트를 조작하고 관찰하는 콘솔. 파이프라인은 원천 중 하나이고, 외부 에이전트(로컬, 타사)도 직접 붙음 | 이 초안 |

orch 안에는 LLM이 없습니다. 요청 해석, 분해, 지시서·테스트 작성, 판정은 메인 Claude Code가 하고(`config/main.md`), 파이프라인은 그 판단이 규칙을 벗어나지 못하게 하는 결정론적 도구입니다.

**파이프라인이 할 수 있는 것**: 대상 등록, 작업별 브랜치·워크트리, 테스트 우선 커밋, 파일 단위 잠금과 동시 실행 상한, Codex·Claude 비대화형 실행(시간 제한, 샌드박스), 결과 분류(보고 누락, 시간 초과, 범위 밖, 한도 오류), G1~G3와 교차 리뷰, rebase·push·PR, 재시도·폐기·재개·강제 종료, doctor·pause·gc·launchd·세션 복원·ntfy, 메인의 레인 우회와 머지 차단.

**파이프라인이 할 수 없는 것**

| 구분 | 내용 | 작업공간이 맡는가 |
| --- | --- | --- |
| 설계상 하지 않음 | 머지, 기본 브랜치 push, force push, CI. 계획(분해·지시서·판정은 메인). diff·테스트로 판정할 수 없는 작업. 메인 세션 자동 재기동 | 아니요. 작업공간도 하지 않음 |
| 지금 구조로는 불가 | Codex·Claude Code 고정 버전 외의 에이전트. 실행 중 에이전트와의 대화나 방향 전환. MCP 호출 관찰. 한 메인 세션에서 여러 대상 | 외부 에이전트 조작, MCP 관찰, 여러 대상 보기는 작업공간이 맡음. 다만 파이프라인 레인으로 들어오는 것은 아님 |
| 측정상 한계 | Claude 잔여 사용량 사전 조회, 토큰 예산 강제, 서버에서 취소된 인증 감지, 테스트 품질을 넘는 검증, 맥 자체의 전원 꺼짐 감지 | 사용량 관찰만 일부(D8) |

**경계** (한 저장소 안에서도 유지)

- 머지될 코드 변경은 **파이프라인만** 만듭니다. 여기에 들어오는 에이전트는 반드시 레인이 되어 게이트를 거칩니다.
- 작업공간에서 조작한 외부 에이전트의 결과물은 파이프라인을 거치기 전까지 대상 저장소에 들어가지 않습니다. 외부 에이전트에게 GitHub App 토큰, orch 명령, 대상 워크트리 쓰기 권한을 주지 않습니다.
- 작업공간은 파이프라인을 계약(8장)으로만 읽고 orch 명령으로만 조작합니다. 파이프라인 코드는 작업공간 코드를 가져오지(import) 않습니다. 이 방향은 테스트로 고정합니다(7장).

## 2. 원칙

- 작업공간은 오케스트레이션 판단을 하지 않습니다. 파이프라인 상태는 계약(8장 ①)으로만 읽고, 동작은 orch 명령으로만 합니다.
- 작업공간은 state.db에 쓰지 않습니다. 실행 로그 형식과 설계 문서의 문구에 의존하지 않습니다.
- 머지와 force push는 어떤 범위에서도 화면에 두지 않습니다(Merge policy).
- 업그레이드는 알리기만 하고 실행하지 않습니다. 고정 버전은 PR과 사용자 승인으로만 바뀝니다.

결정: 작업공간을 이 저장소에 둡니다. 계약 변경과 화면 변경이 한 PR에 들어가고 버전이 하나라 항상 맞습니다. 대신 아래 결과를 다뤄야 합니다.

| 결과 | 대응 |

## 8. 스키마와 프로토콜의 정의 위치 (D9)

원칙: **데이터를 만드는 쪽의 테스트가 형식을 지킵니다.** 모두 이 저장소에 있으므로 형식과 그 테스트는 같은 PR에서 바뀝니다. 허브의 `schemas/result.json`(서브가 만들고 orch가 검증)과 같은 방식입니다.

| 경계 | 만드는 쪽 | 정의하는 곳 | 형식 |
| --- | --- | --- | --- |
| ① 파이프라인 출력 계약: `status`, `show`, `events`, `roadmap`, `versions`, `doctor` | 파이프라인 | `schemas/cli/<명령>.v<N>.json`, 규칙은 `docs/design/` | JSON Schema 2020-12. `events --follow`는 JSON Lines(한 줄에 이벤트 하나, `id`가 단조 증가) |
| ② 작업공간 서버 ↔ 화면 클라이언트: WebSocket 메시지, 터미널 스트림, 레이아웃 상태, 인증 | 작업공간 서버 | `schemas/deck/`와 `docs/design/` | JSON Schema 2020-12 |
| ③ 에이전트 세션 기록(Codex rollout, Claude Code jsonl) | Codex, Claude Code | 외부 형식. `docs/design/`에 고정 버전 기준 측정 결과(W-M1~W-M3) | 읽는 필드만 최소로 |
| ④ 외부 에이전트 조작 | 외부 에이전트 | ACP 표준. 지원하는 ACP 버전과 측정 결과(W-M5)를 `docs/design/`에 | JSON-RPC |
| ⑤ 도구 호출 관찰 | 에이전트 | OpenTelemetry 표준. 읽는 이벤트와 필드를 `docs/design/`에(W-M4) | OTLP |

**① 계약의 규칙**

- 각 출력에 `schema_version`(정수)을 넣습니다. 필드 추가는 같은 버전 안에서 허용하고, 받는 쪽은 모르는 필드를 무시합니다. 필드 삭제, 이름이나 의미 변경, 형식 변경은 버전을 올립니다.
- 한 저장소라 버전이 함께 움직이므로, 이전 버전을 함께 내는 기간은 두지 않습니다. 다만 실행 중인 서버가 설치본보다 오래된 경우를 위해 서버는 버전을 확인합니다(NF-4).
- 계약 테스트는 실제 명령 출력을 `schemas/cli/`의 스키마로 검증하고, G2에서 돕니다.
- `schemas/`는 공유 경로입니다. 스키마 추가는 하네스 PR이나 해당 작업의 테스트 커밋에서 메인이 합니다.
